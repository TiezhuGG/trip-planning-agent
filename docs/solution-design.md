# 方案设计

## 1. 目标定义

项目目标不是生成一段“看起来不错”的旅游文案，而是输出一份可以继续编辑、校验、重规划和导出的结构化多日行程。

核心要求：

- 输入目的地、出行日期、天数、预算和偏好
- 结合真实地图、天气、路线等事实数据，而不是只依赖模型想象
- 输出适合前端直接消费的结构化 JSON
- 支持保存工作区并在后续继续修改
- 支持围绕固定预约继续规划，而不是每次从头生成
- 支持出发前再次校验并快速修复问题

## 2. 核心设计原则

### 2.1 模型负责规划，工具负责补事实

LLM 擅长生成行程骨架、组织表达和做全局编排，但不适合单独承担 POI、天气、路线、营业时间等事实型信息。  
因此系统把“规划”和“事实查询”拆开：

- 模型负责 itinerary 骨架与整体规划
- 地图与天气能力负责事实补全
- 后处理规则负责归一化、校验和收口

### 2.2 输出必须结构化

后端统一输出 schema 化结果，避免前端直接消费自然语言文本。  
这样才能稳定支持：

- 地图渲染
- 日程卡片渲染
- 预算汇总
- 工作区持久化
- 局部重规划
- 预检与修复动作

### 2.3 主链路必须可降级

外部依赖存在限流、网络波动和工具不可用问题，因此需要：

- 主模型失败时切换备用模型
- 限流时走 fallback
- MCP 不可用时由部分 Web Service 兜底
- 对集成状态提供独立诊断接口

### 2.4 从一次生成升级为持续编辑

真实旅游规划不是“一次生成就结束”，而是会不断补充预约、修改偏好和局部调整。  
因此引入 `Trip Workspace` 作为产品级状态载体，而不是只保留一次性生成结果。

## 3. 总体架构

```text
Frontend
  ├─ 规划表单
  ├─ 工作区面板
  ├─ 日程结果区
  └─ 地图展示

Backend API
  ├─ /plans/*
  └─ /trips/*

Planning Layer
  ├─ TravelPlannerService
  └─ Planning Agent Runtime

Capability Layer
  ├─ LLM Client
  ├─ AMap MCP Adapter
  └─ Web Service fallback

Workspace Layer
  ├─ TripWorkspaceService
  ├─ Replan / Precheck / Calendar
  ├─ Reservation rules / audit
  └─ TripWorkspaceStore
```

## 4. 行程生成链路

### 4.1 输入

前端提交 `TripPlanningRequest`，包括：

- `destination`
- `start_date`
- `days`
- `interests`
- `must_visit`
- `pace`
- `budget_level`
- `transport_preferences`
- `hotel_style`
- `dining_preferences`
- `travelers`
- `notes`

### 4.2 编排

行程生成由后端编排层负责，当前整体流程为：

1. 检查 LLM、MCP 和地图能力状态
2. 生成 seed itinerary
3. 查询景点、酒店、天气和路线
4. 汇总为完整 `TravelPlan`
5. 做预算归一化、地图点位整理和诊断收口

### 4.3 输出

最终结果不是一段文本，而是完整的 `PlanningResponse`，主要包括：

- `plan`
- `planning_context`
- `agent_trace`
- `tool_trace`
- `meta`
- `diagnostics`
- `integration_status`

## 5. Trip Workspace 设计

### 5.1 为什么需要工作区

如果只有 `POST /plans/generate`，系统只能做一次性结果展示，无法承接真实产品流程。  
工作区用于保存：

- 请求快照
- 当前结果快照
- 用户备注
- 锁定日期
- 固定预约
- 最近一次重规划摘要
- 最近一次预检摘要
- 版本号与分享 token

### 5.2 当前关键能力

当前工作区已支持：

- 创建工作区
- 保存草稿
- 在已有工作区上继续生成
- 更新备注与锁定日期
- 通过分享 token 读取
- 整程重规划
- 单日重规划
- `fill_gaps` 缺口修复
- 手动刷新出发前预检
- 导出 `.ics`

### 5.3 存储设计

`TripWorkspaceStore` 当前支持：

- `SQLite`
- `JSON`

默认走 `auto`，便于本地开发和轻量部署。

## 6. 固定预约设计

### 6.1 目标

用户经常已经有真实预约，例如：

- 酒店
- 航班
- 火车
- 餐厅
- 门票
- 其他固定活动

系统必须围绕这些约束继续生成，而不是忽略它们。

### 6.2 当前实现方式

预约已作为工作区中的正式结构化实体，而不是备注文本。  
后端会在生成前把以下内容注入请求：

- 工作区备注
- 预约类型、标题、时间窗、地点
- 预约对应 trip day
- 部分重规划的目标日期和原因

当前注入粒度已经扩展到：

- 酒店 `check_in_slot / check_out_slot`
- 非酒店 `anchor_slot`
- 餐厅 `meal_slot`

### 6.3 校验与审计

当前已实现：

- 开始 / 结束时间合法性校验
- 完全落在行程日期外的预约拒绝保存
- 非酒店类预约时间冲突校验
- 生成后预约覆盖诊断 `reservation_coverage`
- 当前端结果未显式落地时自动保底锚定

覆盖诊断会区分：

- `covered`
- `unresolved`
- `pending`

并保留：

- `target_days`
- `matched_days`
- `auto_anchored_days`

## 7. 重规划与缺口修复设计

### 7.1 两类修复模式

当前系统支持两种重规划方式：

- `replace`
  - 直接重新生成目标天
- `fill_gaps`
  - 尽量保留已有内容，只补齐缺口

### 7.2 当前支持的缺口类型

`fill_gaps` 已支持：

- `stay`
- `meal`
- `breakfast`
- `lunch`
- `dinner`
- `snack`
- `activity`
- `reservation`
- `day-plan`

这让系统从“整天重来”升级为“按缺口修复”。

### 7.3 最近一次重规划摘要

工作区会保留 `last_replan_summary`，用于记录：

- 本次是整天重生还是补缺口
- 目标是哪几天
- 修复类型是什么
- 变更亮点有哪些

这样前端可以直接给用户展示“这次到底改了什么”。

## 8. 出发前预检设计

### 8.1 当前预检范围

当前预检会检查：

- 天气风险
- 路线缺失
- 营业时间缺失
- 预约未落地或仅保底注入

### 8.2 预检刷新

工作区支持手动调用预检刷新。刷新时会：

- 用当前请求、备注、预约重新生成
- 更新工作区版本号
- 更新 `response_snapshot`
- 生成 `last_precheck_summary`

### 8.3 预检摘要与动作

预检摘要不仅记录前后状态变化，还会给出按问题类型的修复动作。

当前已支持多动作修复建议，例如：

- 天气
  - 改室内活动
  - 调整出发时段
- 路线
  - 重排路线影响日
  - 压缩跨区往返
- 营业时间
  - 替换活动
  - 调整游玩时段
- 预约
  - 处理预约

这些动作会被前端直接映射到现有 `repair-day-gap` 链路。

## 9. `.ics` 导出设计

### 9.1 设计目标

系统不应只把结果留在页面里，还要允许用户把结果带到已有工具中继续使用。  
因此当前已打通工作区 `.ics` 导出能力。

### 9.2 当前导出范围

当前导出会覆盖：

- 工作区中的预约
- 住宿信息
- 显式时间活动

这让结果可以直接进入系统日历，而不是只能停留在产品页面中。

## 10. 前端设计

前端不只是表单页，而是同时承载三类职责：

- 规划输入
- 工作区编辑
- 结果消费与二次反馈

### 当前主要区域

- 启动表单
- 工作区面板
- 日程卡片
- 地图区
- 调试 / 诊断面板

### 当前前端结构方向

前端已经开始从 `App.vue` 向 composable 和面板组件拆分：

- 页面壳层负责装配
- composable 负责状态、动作和洞察
- 组件负责展示和交互

这个方向是正确的，后续要继续避免新功能回流成大而全页面组件。

## 11. 为什么这样设计

### 11.1 为什么不全靠模型一次输出

因为会带来三个问题：

- 事实信息不稳定
- 输出难以复用
- 无法支持工作区、预检和局部修复

### 11.2 为什么不一开始就做复杂排程引擎

因为当前阶段更重要的是验证产品价值和建立闭环。  
先用“结构化约束注入 + 生成后覆盖诊断 + 保底锚定 + 局部修复”建立产品能力，再逐步往更强的硬约束排程演进，工程成本更可控。

### 11.3 为什么工作区存储不强依赖外部数据库

因为项目同时需要：

- 本地开发友好
- 轻量部署
- 后续可迁移

所以当前先提供 `SQLite / JSON` 双形态存储，而不是一开始就绑定外部数据库。

## 12. 当前已识别的优化点

### 12.1 前端

- `frontend/src/App.vue` 仍需继续保持壳层定位
- 输入页和日程页仍有继续膨胀风险
- 派生计算和动作逻辑适合继续下沉到 composable

### 12.2 后端

- `route_agent_orchestration.py` 仍偏厚
- `ai_client_runtime_adapter.py` 仍较集中
- `amap_mcp_adapter_helpers.py` 仍是地图层热点
- 规划阶段输入输出对象还可继续显式化

### 12.3 产品能力

- 预约约束可继续升级为更强硬约束排程
- 可增加多方案 diff、协作评论和导入能力
- 预检可以从手动刷新继续演进到更主动的提醒机制

## 13. 下一阶段建议

建议按以下顺序推进：

1. 继续收敛热点编排文件，降低维护成本
2. 把预约能力从软约束进一步升级为更强硬约束排程
3. 继续增强缺口修复和修复后 diff
4. 补上导入与导出能力，例如 Google Maps 收藏点导入和更细粒度 `.ics` 导出
5. 增强预检与多方案决策支持

## 14. 一句话总结

这套方案的核心不是“生成一次旅行攻略”，而是把 AI 生成、事实补全、工作区编辑、预约约束、预检修复和日历导出接成了一条连续的产品化链路。
