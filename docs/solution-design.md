# 方案设计

## 1. 目标定义

项目目标不是生成一段“看起来不错”的旅游攻略，而是输出一份可以继续编辑、校验和重规划的多日结构化行程。

核心要求：

- 输入目的地、出行日期、天数、预算、兴趣、出行偏好
- 结合真实地图与天气信息，而不是只依赖模型臆造
- 返回适合前端直接渲染的结构化 JSON
- 支持保存工作区并在后续继续修改
- 支持围绕固定预订继续规划，而不是每次从头生成

## 2. 核心设计原则

### 2.1 模型负责规划，工具负责补真值

LLM 擅长生成行程骨架、组织表达和做全局编排，但不适合单独承担路线、天气、POI 等事实型信息，因此系统把“规划”与“事实查询”拆开。

### 2.2 输出必须结构化

后端统一输出 schema 化结果，避免前端直接消费自然语言文本。这样才能支持：

- 地图渲染
- 日程卡片渲染
- 预算汇总
- 工作区持久化
- 局部重规划

### 2.3 主链路必须可降级

外部依赖存在限流、网络波动和工具不可用问题，因此需要：

- 主模型失败时切备用模型
- 限流时切模板 fallback
- MCP 不可用时由部分 Web Service 兜底
- 对集成状态提供独立诊断接口

### 2.4 从单次生成升级为可持续编辑

真实旅游规划不是“一次生成就结束”，而是会不断补充预订、修改偏好和局部调整，所以引入 `Trip Workspace` 作为产品级状态载体。

## 3. 架构设计

```text
Frontend
  ├─ 规划表单
  ├─ 工作区面板
  ├─ 日程结果区
  └─ 地图展示

Backend API
  ├─ /plans/*
  └─ /trips/*

Planning Layer
  ├─ TravelPlannerService
  └─ PlanningCoordinatorAgent

Capability Layer
  ├─ LLM Client
  ├─ AMap MCP Adapter
  └─ Web Service fallback

Workspace Layer
  ├─ TripWorkspaceService
  ├─ Reservation rules / audit
  └─ TripWorkspaceStore
```

## 4. 行程生成链路

### 4.1 输入

前端提交 `TripPlanningRequest`，包含：

- `destination`
- `start_date`
- `days`
- `interests`
- `must_visit`
- `pace`
- `budget_level`
- `transport_preferences`
- `hotel_style`
- `dining_preferences`
- `travelers`
- `notes`

### 4.2 编排

`PlanningCoordinatorAgent` 负责整体流程：

1. 检查 LLM、MCP、地图能力状态
2. 生成 seed 行程框架
3. 查询景点、酒店、天气和路线
4. 汇总为最终 `TravelPlan`
5. 做预算归一和结果收口

### 4.3 输出

最终返回：

- `plan`
- `planning_context`
- `agent_trace`
- `tool_trace`
- `meta`
- `diagnostics`
- `integration_status`

## 5. Trip Workspace 设计

### 5.1 为什么需要工作区

如果只有 `POST /plans/generate`，系统只能做一次性结果展示，无法承接真实产品流程。工作区用于保存：

- 请求快照
- 当前结果快照
- 用户备注
- 锁定日期
- 固定预订锚点
- 版本号与分享 token

### 5.2 关键能力

当前已实现：

- 创建工作区
- 保存草稿
- 在已有工作区上继续生成
- 更新备注与锁定日期
- 通过分享 token 加载
- 整体重规划
- 按天重规划

### 5.3 数据存储

`TripWorkspaceStore` 当前支持：

- `SQLite`
- `JSON`

默认走 `auto`，便于本地开发和轻量部署。

## 6. 固定预订设计

### 6.1 目标

用户常常已经有部分真实预订，例如：

- 酒店
- 航班
- 火车
- 餐厅
- 门票
- 其他固定活动

系统必须围绕这些约束继续生成，而不是忽略它们。

### 6.2 当前实现方式

后端在生成前会把以下内容拼入有效请求：

- 工作区备注
- 预订类型、标题、时间窗、地点
- 预订对应 trip day
- 部分重规划的目标日期和原因

这套方案本质上是“结构化强提示”，优点是实现成本低、兼容当前生成链路；缺点是仍属于软约束。

### 6.3 校验与审计

目前已实现：

- 开始/结束时间合法性校验
- 完全落在行程日期外的预订拒绝保存
- 非酒店类预订时间冲突校验
- 生成后预订覆盖审计
- 前端展示预订覆盖状态和按天完成度

## 7. 前端设计

前端不只是表单页，而是同时承担三类职责：

- 规划输入
- 工作区编辑
- 结果消费与二次反馈

当前主要区域：

- 启动表单
- 工作区面板
- 日程卡片
- 地图区域
- 调试/诊断面板

新增的工作区洞察逻辑已开始从 `App.vue` 抽离到 composable，方向正确，但还没有彻底拆完。

## 8. 为什么这样设计

### 8.1 不做“全靠模型一次输出”

因为这会带来三个问题：

- 事实信息不稳定
- 输出难以复用
- 无法支持工作区与局部重规划

### 8.2 不直接做复杂排程引擎

因为当前产品阶段更需要快速验证用户价值。先用“结构化约束注入 + 审计反馈”建立闭环，再逐步向硬约束排程演进，工程成本更可控。

### 8.3 不把工作区直接做成数据库强依赖

因为本项目同时需要本地开发友好和可部署性，所以先提供 `SQLite / JSON` 双形态存储，而不是一开始就绑定外部数据库。

## 9. 当前已识别的优化点

### 9.1 前端

- `frontend/src/App.vue` 体量仍偏大
- 工作区状态、通知、URL 同步、请求动作还可以继续拆 composable
- 部分派生计算仍偏重，适合继续模块化

### 9.2 后端

- `backend/app/services/trip_workspace.py` 仍承担较多编排职责
- 预订规则、审计、重规划合并逻辑应继续拆分
- 未来可以把“预订 day 映射”和“重规划合并策略”独立成可测试模块

### 9.3 产品能力

- 预订约束可升级为硬约束排程
- 可增加协作评论、候选方案对比、预算超限提醒
- 可增加出发前 checklist、天气风险提醒、城市内通勤异常预警

## 10. 下一阶段建议

建议按以下顺序推进：

1. 继续完成前后端大文件拆分，降低维护成本
2. 把预订能力从软约束升级到可验证的硬约束排程
3. 补齐协作与出行前提醒类功能，提升产品完整度
4. 引入更明确的 telemetry 和质量评估指标，支撑后续优化
