## 简历详细版

### 项目名称

智能旅游助手 / Trip Planning Agent

### 技术栈

- 前端：Vue 3、TypeScript、Vite
- 后端：FastAPI、Pydantic v2
- 模型层：OpenAI-compatible API、主模型失败切备模
- 地图层：高德 MCP、Web Service fallback
- 存储层：Trip Workspace Store，支持 SQLite / JSON
- 工程化：Docker、GitHub Actions、pytest、前端构建校验

### 项目定位

这个项目不是“让模型生成一段旅游攻略文案”，而是面向真实出行场景，输出可执行、可编辑、可重规划的结构化行程系统。  
用户不只拿到一份结果，还可以把结果保存成工作区，继续补充说明、录入固定预约、锁定某几天、按天重规划，并查看地图、路线和预约覆盖情况。

### 个人职责

- 设计多阶段 Agent 编排链路，串联 seed itinerary、事实数据补全、路线生成、truth binding 和结果收口
- 设计 Trip Workspace 能力，支持草稿保存、结果快照、分享访问、局部重规划和版本演进

### 差异化价值

相比常见“AI 行程生成 Demo”，这个项目的差异点在于：

- 不是只生成文案，而是输出结构化、可执行、可回填的 `TravelPlan`
- 不是只依赖模型想象，而是接入 POI、天气、路线等事实数据
- 不是生成一次就结束，而是支持保存工作区、继续编辑、分享访问和局部重规划
- 不是只记录预约，而是让预约真正进入生成请求，并对结果做覆盖审计
- 不是只给最终答案，而是保留 diagnostics、warnings、telemetry 和集成状态

## 面试口述版

我做的是一个面向真实出行场景的 AI 智能旅游助手。它不是让大模型写一段攻略，而是把 LLM、地图能力、规则校验和工作区编辑串成完整系统。  
用户输入目的地、天数、预算和偏好后，系统会先生成 seed itinerary，再用地图和天气能力补全 POI、酒店、路线和天气，最后组装成结构化多日行程。  
更关键的是，结果不是一次性的，用户可以保存为 Trip Workspace，继续补充说明、录入固定预约、锁定部分日期、发起局部重规划，并检查预约有没有真正落到结果里。

## 当前仍值得优化的地方

### 结构热点

- `backend/app/services/amap_mcp_adapter_helpers.py`
  - 仍偏大，兼顾参数整理、选择辅助、路线辅助和部分适配层胶水逻辑
- `backend/app/services/amap_mcp_adapter.py`
  - 仍然是地图层统一入口，继续拆分可读性会更好
- `backend/app/services/ai_client.py`
  - 已拆分，但入口编排层依然偏重
- `frontend/src/composables/useTripWorkspaceActions.ts`
  - 工作区写操作、通知和重规划反馈仍较集中
- `frontend/src/App.vue`
  - 已明显收缩，但页面级状态编排仍然可以继续下沉

### 产品层优化

- 预约目前是“强约束提示 + 结果审计”，下一步应升级为更明确的硬约束排程
- 目前能发现覆盖缺口，但还缺“按缺口一键补齐”的快捷动作
- 工作区支持分享访问，但还缺多方案对比和变更差异说明
- 地图可展示结果，但还缺导入外部收藏点、导出日历等更贴近真实使用场景的能力

## 下一阶段最实用的功能建议

1. 硬约束预约排程
   把酒店入住、航班/火车、门票和餐厅时间窗显式压进行程槽位，而不只是依赖模型“尽量满足”。
2. 缺口驱动的一键补齐
   当前前端已经能识别哪一天缺酒店、缺餐饮、覆盖不足，下一步应支持直接按缺口触发局部重排。
3. Google Maps 收藏点导入
   允许用户导入已有收藏点或清单，把“已有偏好资产”直接转成候选 POI。
4. 行程/预约 `.ics` 导出
   直接把预约和每日安排导入手机日历，实用性很强。
5. 出发前二次校验
   在最终确认前刷新天气、营业状态、路线耗时和预约冲突，降低信息过期风险。
6. 多方案对比与 diff
   同一请求输出“省钱版 / 均衡版 / 深度版”，并支持工作区级别差异比较。
