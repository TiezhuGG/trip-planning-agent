# 智能旅游助手：代码链路详解与复盘指南

## 版本说明

- 文档基线时间：2026-04-15
- 当前本地基线：
  - 后端：`131 passed, 8 warnings`
  - 前端：`vue-tsc --noEmit` 通过，`npm run build` 通过

这份文档不按目录平铺，而是按“请求如何穿过系统”来解释项目。同时给出一轮完整体检结论，回答四个问题：

1. 主链路现在怎么跑
2. 最近一轮重构后职责边界怎么变了
3. 当前哪些地方已经合理，哪些地方还值得继续收敛
4. 对照竞品之后，下一阶段最值得补哪些功能

## 1. 项目体检结论

### 当前结构已经比较健康的地方

- API 层没有堆业务，`planning.py` 主要承担入参转换和异常边界
- `planner.py`、`planning_agent.py`、`trip_workspace.py` 都已经收缩成更明确的 orchestration 入口
- 前端主页面不再由 `App.vue` 独占所有逻辑，状态、视图模型、事件桥接已经开始成层
- Trip Workspace 与固定预约已经不是“附属功能”，而是进入主链路的正式约束层

### 当前最值得继续关注的热点

- 后端：`route_agent_orchestration.py`、`ai_client_runtime_adapter.py`、`amap_mcp_adapter_helpers.py`
- 前端：`PlannerRequestForm.vue`、`DailyItineraryCard.vue`、页面级 bootstrap / shell 编排
- 领域模型：`backend/app/schemas/planning.py` 仍然承载大量跨层结构，后续可以继续做语义分包

### 总结判断

项目已经从“能跑的 AI demo”进入“可持续迭代的工程底盘”阶段。  
现在不合理的地方不再是“明显写乱了”，而是少数热点文件还承担了过多编排职责，后续新增功能如果继续直接往这些文件里堆，结构会反弹。

## 3. 主链路一：行程生成

### 3.1 API 层

文件：`backend/app/api/routes/planning.py`

关键接口：

- `GET /api/v1/plans/integrations/status`
- `GET /api/v1/plans/telemetry`
- `POST /api/v1/plans/generate`

这一层目前做得比较克制：

- 接收 `TripPlanningRequest`
- 调用 `TravelPlannerService.generate()`
- 统一转换模型、网络、MCP 等异常

这说明主业务没有回流到路由层。

### 3.2 服务入口层

文件：

- `backend/app/services/planner.py`
- `backend/app/services/planner_cache.py`
- `backend/app/services/planner_telemetry.py`

`TravelPlannerService` 现在已经是一个比较清晰的入口服务：

- 调度总控 agent
- 处理生成缓存
- 做并发保护和请求去重
- 记录 telemetry

相对早期版本，这里最大的改善是把“缓存”和“性能观测”从主类里拆成 mixin，主文件明显更像入口而不是杂糅实现。

### 3.3 总控编排层

文件：

- `backend/app/agents/planning_agent.py`
- `backend/app/agents/planning_agent_runtime.py`
- `backend/app/agents/planning_agent_stage_runtime.py`
- `backend/app/agents/planning_agent_diagnostics.py`
- `backend/app/agents/planning_agent_postprocess.py`

当前总体流程：

1. 检查集成状态
2. 生成 seed itinerary
3. 并发拉取天气、POI、酒店候选
4. 组合成完整 `TravelPlan`
5. 做酒店绑定、餐饮绑定、路线生成、truth binding
6. 收口 diagnostics、warnings、telemetry、地图中心点

这里的核心设计并不是“让 LLM 一次写完”，而是把任务拆成：

- 模型负责规划骨架和最终组装
- 工具负责 POI、天气、路线等事实数据
- 规则负责补齐、归一化、审计和降级

这是目前项目最有价值的工程特征。

## 4. 主链路二：Trip Workspace

### 4.1 接口层

同样在 `backend/app/api/routes/planning.py`，工作区相关接口包括：

- `POST /api/v1/trips`
- `GET /api/v1/trips/{trip_id}`
- `GET /api/v1/trips/share/{share_token}`
- `PATCH /api/v1/trips/{trip_id}`
- `POST /api/v1/trips/{trip_id}/replan`

这条链路把项目从“一次生成”升级成“可持续编辑”。

### 4.2 工作区服务层

文件：

- `backend/app/services/trip_workspace.py`
- `backend/app/services/trip_workspace_builders.py`
- `backend/app/services/trip_workspace_replan.py`
- `backend/app/services/trip_workspace_validation.py`
- `backend/app/services/trip_workspace_reservations.py`
- `backend/app/services/trip_workspace_runtime.py`

当前职责边界已经比较清晰：

- `trip_workspace.py`
  - 工作区统一入口
- `trip_workspace_builders.py`
  - create / update 请求和快照构建
- `trip_workspace_replan.py`
  - 整体 / 按天重规划逻辑
- `trip_workspace_validation.py`
  - 快照与状态校验
- `trip_workspace_reservations.py`
  - 预约校验、请求增强、覆盖审计
- `trip_workspace_runtime.py`
  - 运行期辅助能力与流程承接

这说明工作区已经从“几个接口拼起来”变成了一个独立的业务层。

## 5. 地图层链路

### 5.1 当前分层

文件：

- `backend/app/services/amap_mcp_adapter.py`
- `backend/app/services/amap_mcp_adapter_helpers.py`
- `backend/app/services/amap_mcp_adapter_runtime.py`
- `backend/app/services/amap_mcp_route_runtime.py`
- `backend/app/services/amap_mcp_route_support.py`
- `backend/app/services/amap_mcp_route_webservice.py`
- `backend/app/services/amap_mcp_selection.py`
- `backend/app/services/amap_mcp_normalization.py`

当前地图层已经从“大而全适配器”收敛成几层：

- 统一入口：`amap_mcp_adapter.py`
- 参数整理与胶水逻辑：`amap_mcp_adapter_helpers.py`
- 运行时保护与调用策略：`amap_mcp_adapter_runtime.py`
- 路线运行时编排：`amap_mcp_route_runtime.py`
- 路线基础算法：`amap_mcp_route_support.py`
- Web Service 兜底：`amap_mcp_route_webservice.py`
- 选择与打分：`amap_mcp_selection.py`
- 结果归一化：`amap_mcp_normalization.py`

### 5.2 最近一轮拆分的意义

最近这一轮继续把：

- 选择逻辑拆到 geo / cache / location / sorting
- normalization 拆到 poi / weather / route
- adapter 拆到 discovery / route / runtime / helpers

这类拆分的价值不是文件数量变多，而是地图依赖变成了更可测试、更可替换的层次结构。

## 7. 当前哪些地方“不太合理”或“还可以优化”

### 7.1 后端仍偏厚的地方

- `backend/app/agents/route_agent_orchestration.py`
  - 仍然承担较重的日级 / 段级并发编排和 truth binding 流程
- `backend/app/services/ai_client_runtime_adapter.py`
  - LLM 请求运行时、模式切换、重试与降级逻辑仍较集中
- `backend/app/services/amap_mcp_adapter_helpers.py`
  - 仍然是地图层偏大的胶水模块

这些文件不是“有 bug”，而是仍然承担过多 orchestration 细节，后续新增功能最容易再次把它们推厚。

### 7.2 前端仍偏热的地方

- `frontend/src/components/PlannerRequestForm.vue`
  - 仍是输入页核心热点，未来功能一多很容易再次变厚
- `frontend/src/components/DailyItineraryCard.vue`
  - 结果展示细节多，后续功能回流风险高
- 页面 bootstrap
  - 目前 `App.vue` 已经明显收缩，但初始化与跨模块装配仍然值得继续控制

### 7.3 领域结构上还可以继续做的事

- `backend/app/schemas/planning.py` 仍然装了较多跨层对象
- planning 阶段上下文目前更多依赖约定组合，后续可以继续显式化输入/输出对象
- 导出边界还可以更清楚地区分“稳定公共 API”和“内部支持模块”

## 8. 推荐的下一轮技术优化顺序

1. 标准化 planning 阶段上下文
   先把阶段输入/输出对象收敛，再继续拆 `planning_agent_runtime.py` 一类编排文件。
2. 继续收缩路由编排热点
   优先处理 `route_agent_orchestration.py` 的 truth binding 与 route gathering 两条链。
3. 让页面壳层只保留装配
   如果后续继续加功能，优先新增 shell/bootstrap composable，而不是让 `App.vue` 回胖。
4. 控制地图层公共出口
   明确稳定导出、内部 support 和 Web Service 专用实现，减少兼容层长期累积。

## 9. 对照竞品，下一阶段最值得补的功能

从代码现状和竞品公开能力一起看，最值得补的不是再做一个聊天入口，而是把现有工作区能力做得更可落地：

1. 预约硬约束排程
2. 缺口驱动的一键补齐
3. Google Maps 收藏点 / 清单导入
4. 行程与预约 `.ics` 导出
5. 出发前二次校验
6. 多方案对比与 diff

这些能力和现有 Trip Workspace、预约审计、局部重规划天然连得上，工程投入和产品价值的比值最高。


- 稳定公共出口
- 仅内部使用的 support 函数
- Web Service 专用实现

避免 helper 模块长期直接依赖 runtime 内部细节。

### 8.2 工作区前端动作层仍偏“厚”

`useTripWorkspaceActions.ts` 同时承担：

- API 写操作
- 当前工作区存在性校验
- 用户提示文案
- 单日重规划和整体重规划反馈

后续如果继续加“缺口补齐”“多方案比较”“导出”等能力，这里会再次膨胀。

### 8.3 编排层的阶段状态对象还可以再标准化

`planning_agent_runtime.py` 已经比之前轻很多，但阶段之间传递的数据结构仍偏松散。  
如果继续增强可观测性，建议把各阶段输入/输出再显式封装，减少长参数列表与上下文隐式耦合。

### 8.4 文档和命令入口要尽量统一

用户之前遇到过“.venv 已安装但 pytest 无法执行”的问题，本质上是执行位置与解释器路径不一致。  
文档应始终给出两套等价命令：

- 仓库根目录执行
- 进入 `backend` 目录后执行

这样更适合真实协作场景。

## 9. 结合竞品，还能补哪些实用功能

基于 2026-04-11 查到的官方公开能力，可以把竞品粗分成三类：

- Mindtrip
  - 强在灵感发现、协作、地图、收藏与收据/确认单整理
- Wonderplan
  - 强在快速生成、简单编辑、离线 PDF
- GuideGeek
  - 强在对话式问答、实时价格/本地建议
- Google Maps
  - 强在真实导航、收藏点、出发时间规划和日常路线保存

对照当前项目，最值得补的不是“再做一个聊天框”，而是把现有工作区能力做得更可落地：

1. 预约硬约束排程
2. 缺口驱动的一键补齐
3. Google Maps 收藏点 / 清单导入
4. 行程与预约 `.ics` 导出
5. 出发前二次校验
6. 多方案对比与差异说明
7. 票据 / 确认单导入并自动映射到预约

## 10. 推荐的下一步技术改造顺序

1. 收紧地图层公共出口
   先固定 `amap_mcp_route_runtime.py` 的兼容边界，再逐步减少 helper 对内部细节的依赖。
2. 拆薄 `useTripWorkspaceActions.ts`
   把 workspace guard、notice 文案、reservation mutation、replan mutation 分开。
3. 标准化 planning 阶段上下文
   给阶段输入输出引入更显式的结构，减少隐式耦合。
4. 增加功能级验证用例
   重点覆盖预约硬约束、缺口补齐、导入导出和出发前校验。
