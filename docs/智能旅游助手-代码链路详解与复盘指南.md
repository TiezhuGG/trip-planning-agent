# 智能旅游助手：代码链路详解与复盘指南

## 版本说明

- 文档基线时间：2026-04-15
- 当前本地回归基线：
  - 后端：`157 passed, 10 warnings`
  - 前端：`vue-tsc --noEmit` 通过，`npm run build` 通过

这份文档不按目录平铺讲文件，而是按“用户请求如何穿过系统”来说明当前项目的主链路、职责边界、近期新增能力和后续可继续优化的热点。

## 1. 当前项目处于什么阶段

这个项目已经不是“能跑通一次生成”的 AI Demo，而是一个具备持续编辑能力的旅行工作台。

当前系统已经形成两条稳定主链路：

1. 行程生成链路
   从用户输入到结构化多日 `TravelPlan` 输出。
2. Trip Workspace 链路
   从一次性结果进入“可保存、可修改、可重规划、可分享、可导出”的持续工作流。

最近一轮迭代把几个过去只做到“提示”的能力，进一步推进成了“可直接执行”的能力：

- `.ics` 日历导出已经贯通到工作区
- 预约不只做校验，也支持保底锚定回写到日程
- 同日多预约已经支持顺序协调和保底顺序锚定
- 单日重规划不只支持整天重生，也支持 `fill_gaps`
- `fill_gaps` 已细化到早餐、午餐、晚餐、加餐
- 工作区会记录最近一次重规划摘要 `last_replan_summary`
- 工作区支持出发前预检刷新 `refresh_precheck`
- 工作区会记录最近一次预检摘要 `last_precheck_summary`
- 预检摘要已支持按问题类型输出多个修复动作

## 3. 主链路一：行程生成

### 3.1 API 层

入口在 `backend/app/api/routes/planning.py`，核心接口包括：

- `GET /api/v1/plans/integrations/status`
- `GET /api/v1/plans/telemetry`
- `POST /api/v1/plans/generate`

这一层当前比较干净，主要职责是：

- 接收 `TripPlanningRequest`
- 调用 `TravelPlannerService.generate()`
- 做统一异常转换
- 返回结构化结果

当前 API 层没有明显堆业务逻辑，这是健康信号。

### 3.2 服务入口层

核心入口在 `backend/app/services/planner.py`。

`TravelPlannerService` 目前已经是一个比较清晰的 orchestration 入口，负责：

- 请求去重
- 缓存命中
- 调用主编排 Agent
- 记录 telemetry
- 返回最终 `PlanningResponse`

过去很多杂项逻辑已经下沉到：

- `planner_cache.py`
- `planner_telemetry.py`

这说明主服务正在从“大而全执行器”回到“编排入口”。

### 3.3 Agent 编排层

核心文件包括：

- `backend/app/agents/planning_agent.py`
- `backend/app/agents/planning_agent_runtime.py`
- `backend/app/agents/planning_agent_stage_runtime.py`
- `backend/app/agents/planning_agent_diagnostics.py`
- `backend/app/agents/planning_agent_postprocess.py`

当前整体思路不是让 LLM 一次写完，而是拆成多阶段：

1. 生成初始 itinerary 骨架
2. 拉取 POI、酒店、天气、路线等事实数据
3. 组合为完整 `TravelPlan`
4. 做归一化、补齐、后处理和诊断收口

这是项目最有价值的工程设计之一，因为它天然支持：

- fallback
- 诊断
- 回归测试
- 针对单阶段优化

## 4. 主链路二：Trip Workspace

### 4.1 为什么 Trip Workspace 是主链路

Trip Workspace 是项目产品化的关键分水岭。

没有工作区时，系统只能“一次生成”。  
有了工作区后，系统支持：

- 保存请求和结果快照
- 记录人工备注
- 录入固定预约
- 锁定部分日期
- 单日或整程重规划
- 保存最近一次重规划摘要
- 手动刷新出发前预检
- 保存最近一次预检摘要
- 分享访问
- 导出 `.ics`

### 4.2 工作区 API

接口同样集中在 `backend/app/api/routes/planning.py`：

- `POST /api/v1/trips`
- `GET /api/v1/trips/{trip_id}`
- `GET /api/v1/trips/share/{share_token}`
- `PATCH /api/v1/trips/{trip_id}`
- `POST /api/v1/trips/{trip_id}/replan`
- `POST /api/v1/trips/{trip_id}/precheck`
- `GET /api/v1/trips/{trip_id}/export/ics`

### 4.3 工作区服务层的职责划分

核心文件：

- `trip_workspace.py`
- `trip_workspace_builders.py`
- `trip_workspace_replan.py`
- `trip_workspace_validation.py`
- `trip_workspace_reservations.py`
- `trip_workspace_runtime.py`
- `trip_workspace_precheck.py`
- `trip_workspace_calendar.py`

当前职责边界已经比早期清晰很多：

- `trip_workspace.py`
  - 工作区统一入口
- `trip_workspace_builders.py`
  - 请求、快照和工作区对象构建
- `trip_workspace_replan.py`
  - 重规划和缺口修复
- `trip_workspace_validation.py`
  - 工作区约束和状态校验
- `trip_workspace_reservations.py`
  - 预约校验、注入、覆盖诊断
- `trip_workspace_runtime.py`
  - 工作区运行期结果补齐
- `trip_workspace_precheck.py`
  - 预检摘要与动作建议
- `trip_workspace_calendar.py`
  - `.ics` 导出

## 5. 预约链路：从“备注”升级为正式约束

这是最近最重要的升级之一。

### 5.1 当前能力

预约已经不是简单备注，而是工作区中的结构化实体：

- 支持酒店、航班、火车、餐厅、门票、其他预约
- 做时间合法性校验
- 对非酒店预约做冲突校验
- 在生成前把预约信息显式注入规划请求
- 在生成后做覆盖诊断 `reservation_coverage`
- 必要时做保底锚定回写

### 5.2 预约注入的粒度

当前预约指令已经比早期细很多，主要包括：

- 酒店：`check_in_slot` / `check_out_slot`
- 非酒店：`anchor_slot`
- 餐厅：`meal_slot`

这意味着模型拿到的不只是“有个预约”，而是“这个预约应该落在哪个时间窗”。

最近一轮又补上了同日多锚点协调提示，生成阶段会额外注入：

- `day_anchor_plan=dayN`
- 同一天多个预约的先后顺序
- 锚点之间的换乘 / 等待 buffer
- 酒店和餐厅场景下的额外约束

这一步很关键，因为它把“单个预约能不能落地”升级成了“同一天多个硬约束能不能一起成立”。

### 5.3 生成后的覆盖诊断

结果里已经有结构化的 `reservation_coverage`，会区分：

- `covered`
- `unresolved`
- `pending`

并保留：

- `target_days`
- `matched_days`
- `auto_anchored_days`
- `coordinated_days`
- `coordination_tip`

这使前端不必靠字符串猜测预约有没有真正落地。

如果生成结果仍未完整覆盖预约，后处理还会按时间顺序做保底锚定，并把类似 `固定预约顺序：09:30 Museum Entry -> 19:00 Night River Cruise` 的说明回写到当天提示中。

### 5.4 前端如何把预约解释清楚

前端现在不只展示“覆盖 / 未覆盖”计数，还会继续暴露：

- 哪些预约是保底注入的
- 哪些天做了多锚点协调
- 每天的协调说明
- 针对缺口的直接修复动作

这部分能力主要落在：

- `tripWorkspaceReservationCoverageHelpers.ts`
- `tripWorkspaceDayReadinessHelpers.ts`
- `PlannerReservationInsights.vue`

结果是用户不只能看到“有问题”，还能直接看到“问题落在哪一天、为什么这样排、下一步怎么修”。

## 6. 重规划链路：从整天重生到缺口修复

### 6.1 当前重规划模式

当前重规划已经分为两类：

- `repair_mode="replace"`
  - 整体重新生成目标天
- `repair_mode="fill_gaps"`
  - 在尽量保留已有内容的前提下补缺口

### 6.2 当前支持的缺口类型

`fill_gaps` 已支持：

- `stay`
- `meal`
- `breakfast`
- `lunch`
- `dinner`
- `snack`
- `activity`
- `reservation`
- `day-plan`

其中餐饮已经细到字段级修复，而不是一刀切地重做整个餐饮段。

### 6.3 最近一次重规划摘要

工作区会保留 `last_replan_summary`，用于前端展示：

- 本次是整天重生还是补缺口
- 目标是哪几天
- 修复类型是什么
- 具体变更亮点有哪些

这比只提示“重规划成功”更接近真实可用产品。

## 7. 出发前预检链路：从提示升级为动作面板

### 7.1 当前预检覆盖范围

当前预检会检查：

- 天气风险
- 路线缺失
- 营业时间缺失
- 预约未落地或仅保底注入

### 7.2 预检刷新机制

工作区支持手动调用：

- `POST /api/v1/trips/{trip_id}/precheck`

刷新时会：

- 基于当前工作区请求、备注、预约重新生成结果
- 更新工作区版本号
- 更新 `response_snapshot`
- 生成 `last_precheck_summary`

### 7.3 预检摘要能力

`last_precheck_summary` 当前已保留：

- 刷新前状态
- 刷新后状态
- 变化涉及的天数
- 每一项的 before / after summary
- 推荐修复动作

### 7.4 预检动作已经支持多动作

当前不是每种问题只给一个按钮，而是可返回多个修复动作。

例如：

- `weather`
  - `改室内活动`
  - `调整出发时段`
- `route`
  - `重排路线影响日`
  - `压缩跨区往返`
- `opening-hours`
  - `替换活动`
  - `调整游玩时段`
- `reservation`
  - `处理预约`

前端会按天渲染这些动作，并复用现有 `repair-day-gap` 链路。

## 8. 前端链路：壳层、桥接和工作区面板

### 8.1 当前前端结构已经明显收缩

核心装配点：

- `frontend/src/App.vue`
- `frontend/src/composables/usePlannerViewModels.ts`
- `frontend/src/composables/usePlannerAppBridge.ts`

当前 `App.vue` 更像页面壳层，不再直接承载所有业务逻辑。

### 8.2 工作区动作与洞察拆分

关键 composables：

- `useTripWorkspaceActions.ts`
- `tripWorkspacePersistenceActions.ts`
- `tripWorkspaceReplanActions.ts`
- `useTripWorkspaceInsights.ts`
- `tripWorkspaceReservationCoverageHelpers.ts`
- `tripWorkspaceDayReadinessHelpers.ts`
- `tripWorkspaceDeparturePrecheckHelpers.ts`

这一层的好处是：

- 状态和动作能单独测试
- 视图层只负责展示
- 工作区功能继续扩展时不必把逻辑都堆回 `App.vue`

### 8.3 关键组件

- `TripWorkspacePanel.vue`
- `PlannerWorkspaceSummary.vue`
- `PlannerReservationPanel.vue`
- `PlannerReservationInsights.vue`
- `DeparturePrecheckPanel.vue`

当前这套组件已经不只是“显示结果”，而是承接工作区中的持续操作。

最近一轮前端还补强了两个关键可解释性点：

- 预约覆盖卡片会显示“保底注入”和“多锚点协调”标签
- 日准备度卡片会显示预约协调摘要，并直接提供补住宿 / 补餐饮 / 落地预约等修复动作

## 9. 当前哪些地方已经合理

### 9.1 已经比较健康的点

- API 层没有明显回流业务逻辑
- `planner.py`、`planning_agent.py`、`trip_workspace.py` 都在向入口层收敛
- 工作区能力已经是主链路，而不是侧边附属功能
- 前端在往“壳层 + composable + 面板组件”方向演进
- 预约覆盖诊断和预检动作已经结构化，不依赖字符串猜测

### 9.2 最近新增能力之间是相互复用的

最近这批功能不是孤立堆上去的，而是互相复用：

- 预检动作复用 `repair-day-gap`
- 缺口修复复用工作区重规划
- 预约保底锚定复用结果后处理
- `.ics` 导出复用工作区中的预约和日程信息
- 预检刷新复用工作区重新生成能力

这说明主链路正在形成“平台化能力”，不是一次性的功能拼装。

## 12. 推荐的下一轮产品扩展方向

从当前代码和主链路来看，最值得继续做的不是再加一个聊天入口，而是继续增强工作区。

优先级更高的方向：

1. 预约硬约束排程继续做深
2. 更细粒度的缺口修复
3. Google Maps 收藏点 / 清单导入
4. 更完整的 `.ics` 导出粒度控制
5. 多方案对比与 diff
6. 出发前预检的自动触发策略

## 14. 一句话复盘

当前项目最核心的变化，不是功能数量变多，而是已经把“生成、约束、修复、预检、导出”几条链路接成了一个连续工作流。后续优化重点应放在继续收敛热点文件，以及把工作区做成更强的持续编辑和决策平台。
