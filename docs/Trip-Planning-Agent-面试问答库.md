## 30 秒项目介绍

我做的是一个 AI 智能旅行规划系统，前端用 Vue 3，后端用 FastAPI。用户输入目的地、出发日期、天数、兴趣、预算、交通和住宿偏好后，系统会先用大模型生成一个初步行程骨架，再通过高德地图 MCP 和 Web Service 补齐景点、餐饮、酒店、天气和路线信息，最后输出结构化的多日 itinerary。项目里我重点做了多 Agent 编排、LLM 结构化输出稳定性、地图工具调用兜底，以及前端地图渲染和 PNG/PDF 导出。

## 1 分钟项目介绍

这个项目是一个面向旅行场景的多 Agent 智能规划系统。整体上是 Vue 3 + TypeScript + Vite 的前端，加 FastAPI + Pydantic 的后端。核心流程是用户提交旅行参数后，后端的 `PlanningCoordinatorAgent` 会先调用 `PlannerSeedAgent` 用 LLM 生成初步行程骨架，然后通过 `POI`、`Hotel`、`Weather`、`Meal`、`Route` 等子 Agent 去拉取和组织外部事实数据，最后再交给 `ItineraryComposerAgent` 汇总成结构化的最终行程。

我在实现时没有把它做成一次性的大模型文本生成，而是做成了“LLM 负责规划和汇总，工具负责事实补齐，规则负责校验和修复”的模式。这样做的好处是结果更可控，也更方便调试。后端支持 JSON-only 输出、重试、结果修复、天数和 `day_number` 严格校验、每日三餐补全、预算重新聚合。前端除了表单和结果展示，还支持高德地图点位和路线渲染、Agent/Tool trace 展示，以及 PNG/PDF 导出。工程化上我还补了 Docker Compose 和 GitHub Actions 自动部署链路。

## 一、项目总览与业务价值

### Q1：你这个项目是做什么的？

**参考回答：**  
这是一个 AI 智能旅行规划系统。用户输入目的地、出发日期、天数、兴趣、预算、交通偏好、住宿风格和餐饮偏好后，系统会自动生成一个结构化的多日旅行计划。最终结果不只是自然语言描述，还包括每天的活动安排、三餐建议、住宿建议、天气信息、路线摘要、预算拆解和地图可视化结果。

### Q2：你为什么想做这个项目？

**参考回答：**  
我想解决的是“旅行计划生成不稳定、信息分散、结果不够可执行”这个问题。很多 AI 旅行助手只会输出一段文案，但真正出行时还需要景点、酒店、餐饮、天气、路线这些外部事实数据。我这个项目的目标就是把大模型的规划能力和地图工具的数据能力结合起来，产出更结构化、更可验证、更接近真实使用场景的结果。

### Q3：这个项目的核心亮点是什么？

**参考回答：**  
我觉得有三个核心亮点。第一是多 Agent 编排，把行程生成拆成种子规划、POI 检索、天气、酒店、路线和最终汇总几个阶段。第二是结构化输出稳定性，我没有直接信任大模型，而是加了 schema 校验、重试、修复、三餐补全和预算重算。第三是工具集成和兜底能力，高德地图既支持 MCP，也支持 Web Service fallback，这让整个流程更稳定。

### Q4：这个项目和普通“调用大模型生成文案”的项目有什么区别？

**参考回答：**  
区别在于我做的是“规划系统”，不是“文案生成器”。普通项目可能只让大模型返回一段行程建议，而我这里后端定义了明确的请求和响应 schema，返回的是结构化 JSON。LLM 只负责生成初步骨架和最终汇总，中间的景点、餐饮、酒店、天气、路线这些事实信息主要由地图工具提供，最后再通过规则校验保证结果完整性和一致性。

### Q5：这个项目的目标用户是谁？

**参考回答：**  
从产品形态上看，目标用户是需要快速获得多日旅行方案的人，尤其是希望一次看到景点、餐饮、住宿、预算和路线的人。从工程角度看，这个项目也适合作为一个 AI Agent 编排样例，展示如何把大模型和外部工具结合，做成一个结构化、可解释的系统。

### Q6：这个项目最重要的业务输出是什么？

**参考回答：**  
最重要的输出是一个结构化的 `PlanningResponse`。里面既有 `initial_plan`，也有 `planning_context`、`agent_trace`、`tool_trace`、`integration_status` 和最终的 `plan`。真正面向用户的是 `plan`，里面包含标题、摘要、天气总结、订票建议、预算、住宿推荐、城市建议、携带清单和每天的具体安排。

### Q7：如果你要一句话概括这个项目，你会怎么说？

**参考回答：**  
我会说这是一个“用多 Agent 编排把 LLM 规划能力和地图工具能力结合起来，生成结构化旅行行程的 AI 系统”。

### Q8：你在这个项目里最核心的工作是什么？

**参考回答：**  
我最核心的工作是把整个链路设计成可控的多阶段流程，而不是一次性生成。我重点做了 Agent 编排、LLM 结构化输出与校验、地图工具接入与降级、前端结果可视化，以及测试和部署链路。面试里我通常会把重点放在后端编排和稳定性设计上，因为这是这个项目最有区分度的部分。

## 二、AI Agent 架构与 LLM 编排

### Q9：为什么要做成多 Agent，而不是单次大模型生成？

**参考回答：**  
因为旅行规划天然是一个多阶段问题。单次生成的问题是，大模型容易编造景点、餐厅、天气和路线，而且结果不稳定。多 Agent 的好处是把任务拆成几个相对清晰的职责：LLM 先给出行程骨架，工具补事实，再由 LLM 汇总。这样每一步更容易观测，也更容易做失败处理和局部降级。

### Q10：你这个项目里有哪些 Agent？

**参考回答：**  
后端一共有 7 个子 Agent。分别是 `PlannerSeedAgent`、`SightseeingAgent`、`HotelRecommendationAgent`、`WeatherAgent`、`MealRecommendationAgent`、`RoutePlanningAgent` 和 `ItineraryComposerAgent`。最外层由 `PlanningCoordinatorAgent` 统一负责调度和组装结果。

### Q11：各个 Agent 是怎么分工的？

**参考回答：**  
`PlannerSeedAgent` 负责生成初步行程骨架，也就是每天的主题、focus、基础 POI 查询词和餐饮查询词。`SightseeingAgent` 负责景点和餐饮候选检索。`HotelRecommendationAgent` 负责酒店候选。`WeatherAgent` 拉天气。`MealRecommendationAgent` 会基于餐饮候选为每天做简单分配。`RoutePlanningAgent` 负责把酒店、景点和餐饮节点串成路线。最后 `ItineraryComposerAgent` 把这些上下文和工具结果汇总成最终 itinerary。

### Q12：整个 Agent 编排流程是什么？

**参考回答：**  
用户请求进来后，协调器会先做集成状态检查，确认 MCP 工具映射和大模型配置是可用的。然后先调用 `PlannerSeedAgent` 生成初步草案，再调用 `SightseeingAgent` 获取景点和餐饮候选。天气和酒店是并发拉取的，之后根据餐饮候选做每日餐饮匹配，再做路线规划，最后把初步草案、上下文和工具轨迹交给 `ItineraryComposerAgent` 生成最终结构化行程。

### Q13：为什么要先生成 initial plan，再查工具数据？

**参考回答：**  
因为 initial plan 相当于整个流程的“意图骨架”。它先明确每天的主题和 focus，后续景点、餐饮、路线的检索就更有方向，不是完全盲搜。这样做一方面能让工具查询更贴近用户意图，另一方面也能让最终汇总时，LLM 有一个稳定的参考框架。

### Q14：LLM 在你的系统里到底负责什么？

**参考回答：**  
LLM 主要负责两个阶段。第一阶段是生成初步行程骨架，第二阶段是把已有的结构化上下文汇总成最终计划。也就是说，LLM 负责“规划”和“组织表达”，而不是直接负责所有事实。事实性比较强的数据，比如 POI、天气、路线，尽量交给工具层来提供。

### Q15：规则层在你的系统里负责什么？

**参考回答：**  
规则层主要负责结果约束和修复。比如检查初步草案的天数是否和请求一致，`day_number` 是否连续；最终计划里每天是否至少有一个活动；三餐是否覆盖；预算是否按每日明细重新聚合；如果 meal type 用了中文别名，也会做归一化。我的思路是让 LLM 负责生成，让规则负责兜底。

### Q16：你怎么保证 LLM 返回的是结构化 JSON？

**参考回答：**  
我在 `TravelAIClient` 里统一封装了请求逻辑，system prompt 明确要求“Return JSON only”，同时传入一个 `response_schema_hint` 作为输出提示。拿到模型结果后，不是直接信任，而是先抽取 JSON payload，再用 Pydantic schema 做验证。如果字段缺失或者结构不符合预期，会触发重试或修复逻辑。

### Q17：如果大模型输出不稳定，你是怎么处理的？

**参考回答：**  
我做了几层处理。第一层是 prompt 和 schema hint 约束。第二层是重试，初步草案和最终汇总都有不同的重试策略。第三层是修复，比如最终计划天数不一致时，会尝试触发补全修复。第四层是后置归一化和严格校验，比如 meal type 别名转换、三餐补全、预算重算、`day_number` 连续性检查。这样即使大模型输出不完美，也能把结果收敛到可用格式。

### Q18：你为什么没有完全依赖 function calling？

**参考回答：**  
这个项目里我更强调的是“最终结果的结构化控制”，而不是让模型自主调用所有工具。因为工具链本身已经由后端 Agent 编排好了，我只需要模型在两个环节输出稳定 JSON。这样比完全把工具调用交给模型更容易控制，也更方便做失败处理、缓存和调试。

### Q19：你的 seed 阶段为什么要单独做重试策略？

**参考回答：**  
因为 seed 阶段相当于整个链路的起点，一旦天数、主题或者基础查询词出错，后面所有工具调用都会偏掉。所以我把 seed 阶段单独做了多轮重试，温度和 token 配置会逐步调整，尽量先把这个“骨架”做稳。

### Q20：compose 阶段为什么也要单独处理？

**参考回答：**  
因为 compose 阶段面对的输入更复杂，除了用户请求，还有 initial plan、POI、天气、酒店、路线和工具轨迹。这个阶段最容易出现的问题不是“完全生成不了”，而是字段缺失、天数不一致、meal 字段别名不统一之类的问题。所以 compose 阶段除了重试，我还额外加了结果修复和归一化。

### Q21：你的 Agent 设计里有真正的“自主决策”吗？

**参考回答：**  
从严格意义上讲，这个项目更偏“编排式多 Agent”，不是完全开放式自主 Agent。每个 Agent 的职责和顺序基本是预定义的，只有在 LLM 生成内容和工具返回结果上有一定动态性。我这样设计是为了先保证可控性和稳定性，因为旅行规划这种业务场景对结构和事实一致性要求比较高。

### Q22：为什么要保留 agent_trace 和 tool_trace？

**参考回答：**  
这是为了可解释性和调试效率。`agent_trace` 记录每个 Agent 是否成功、是否用了 LLM、用了哪些工具、有没有 warning；`tool_trace` 则保留具体的工具名、参数、成功与否和摘要。这样一旦结果不对，我可以快速判断问题是出在 seed、POI、天气、路线还是最终汇总，而不是只能看一个黑盒结果。

### Q23：你的系统里哪些阶段用了并发？

**参考回答：**  
比较明确的一处是酒店和天气查询会并发执行。因为它们都依赖已有的目的地和景点上下文，但彼此之间没有强依赖，所以可以并行。这样可以减少总等待时间，而且测试里我也专门验证了这个并行编排行为。

### Q24：如果某个 Agent 失败了，系统会怎样？

**参考回答：**  
这要看失败类型。像天气这种辅助信息失败，我会记录 warning，并继续生成行程；因为天气不会阻断整个 itinerary。可如果 MCP 没配置、大模型没配置，或者关键工具映射缺失，那就直接失败，因为这会影响结果的稳定性和可验证性。也就是说，我对不同阶段定义了不同的容错级别。

### Q25：为什么天气失败可以继续，MCP 缺失却不行？

**参考回答：**  
因为天气在我的设计里是增强信息，不是核心事实源；没有天气，行程还能生成，只是少一些建议。但 MCP 对景点、餐饮、酒店、路线这些核心事实数据至关重要，如果没有它，就很难生成“稳定可验证”的结果。所以我把天气定义成可降级项，把地图核心工具定义成硬依赖。

### Q26：如果让你继续优化 Agent 架构，你会做什么？

**参考回答：**  
我会优先做三件事。第一是加更细的缓存和可观测性，比如按城市和查询词做 POI 缓存，按阶段记录耗时和失败率。第二是把 route 和 hotel 选择做得更智能一点，比如引入更明确的打分和排序策略。第三是把当前编排式多 Agent 往更强的 planner-executor 模式推进，但前提是先保证结构稳定和成本可控。

## 三、后端设计与稳定性

### Q27：后端整体架构是怎样的？

**参考回答：**  
后端基于 FastAPI，入口在 `app.main`。API 层对外暴露健康检查和规划接口，服务层 `TravelPlannerService` 负责调用编排器，核心业务逻辑在 `PlanningCoordinatorAgent`、`TravelAIClient` 和 `AmapMCPAdapter`。Schema 全部用 Pydantic 定义，请求和响应结构比较明确，便于验证和前后端协作。

### Q28：为什么用 FastAPI？

**参考回答：**  
主要是因为它比较适合这种结构化 API 服务。第一，Pydantic 集成很好，请求和响应 schema 很自然。第二，异步支持比较方便，适合这种既要调用 LLM 又要调外部地图服务的场景。第三，对接口调试和后续扩展也比较友好。

### Q29：你的请求参数有什么约束？

**参考回答：**  
`TripPlanningRequest` 里对很多字段做了约束，比如 `days` 限制在 1 到 14 天，成人数至少 1，儿童和老人数量也有上限。一个比较显式的约束是 `destination` 目前只支持中文城市名，我用了正则做校验。这个约束主要是为了和当前地图查询、提示词语言以及数据源一致，先保证结果稳定。

### Q30：为什么目的地只支持中文城市名？

**参考回答：**  
因为当前项目主要面向中文旅行场景，而且后端对提示词、地图查询和结果展示都是中文优先。如果允许英文城市名或更复杂的国际化输入，工具查询、名称归一化、地理歧义处理都会复杂很多。我先把输入边界收紧，保证主路径稳定，后续如果要扩展，再做更完整的国际化支持。

### Q31：你怎么做 MCP 接入的？

**参考回答：**  
我封装了一个 `AmapMCPAdapter`，底层通过 `MCPStdioClient` 去连接高德 MCP 服务。适配层会负责工具目录缓存、工具名解析、POI 搜索、天气查询、路线规划、坐标补全和工具诊断。这样业务层只需要按“获取景点”“获取天气”“规划路线”这些语义能力来调用，不需要直接关心底层协议细节。

### Q32：为什么还要做 Web Service fallback？

**参考回答：**  
因为实际接入时，MCP 工具不一定总是稳定，比如工具名映射、限流或者某些模式下返回结果不完整。路线规划这类能力如果完全依赖 MCP，稳定性会受影响。所以我在适配层里保留了高德 Web Service 的兜底通道，特别是路线和公交这类结果，更适合保留 fallback。

### Q33：路线规划是怎么做的？

**参考回答：**  
路线规划由 `RoutePlanningAgent` 负责。它会先从当天景点、餐饮和酒店里挑出有坐标的节点，确定起点后拆成多段 segment，再逐段调用适配层的 `plan_route`。适配层会优先尝试 MCP 的坐标或地址工具，如果失败再尝试 Web Service fallback。最后把距离、时长、步骤、polyline 等信息整理成 `RouteSummary`。

### Q34：为什么你的路线是“分段路线”，不是整天只给一条总路线？

**参考回答：**  
因为前端展示和用户理解上，分段路线更直观。比如酒店到景点 1、景点 1 到景点 2、再到餐饮点，这种结构更符合一天的出行过程。工程上分段也更容易调试和降级，某一段失败不会影响整天所有路线的可视化。

### Q35：如果景点没有坐标怎么办？

**参考回答：**  
适配层会尽量通过 POI detail 或 geocode 补坐标，并且做了缓存，避免重复请求。如果某些点最终还是没有坐标，路线规划阶段会过滤掉这些节点，只用有坐标的点来规划。测试里我也验证过这种过滤逻辑，保证不会因为少量无坐标点就导致整天路线完全失败。

### Q36：你怎么做预算计算？

**参考回答：**  
我没有完全信任大模型给出的预算文本，而是做了确定性聚合。每天都有 `cost_breakdown`，里面分住宿、交通、餐饮、门票和额外开销。最终预算会根据这些每日明细重新聚合成总预算，保证预算结果和每日行程是一致的，这样比只让模型返回一句“总预算大概多少”更可靠。

### Q37：你怎么保证最终结果完整？

**参考回答：**  
我主要做了三类检查。第一类是结构检查，比如天数必须和请求一致，`day_number` 必须连续。第二类是内容检查，比如每一天至少要有一个活动，并且默认补齐早餐、午餐、晚餐。第三类是数值一致性，比如餐饮费用和总费用会按补齐后的明细重新计算。只有通过这些检查后，结果才会返回给前端。

### Q38：你的重试策略是怎么设计的？

**参考回答：**  
seed 和 compose 两个阶段各有自己的重试策略。seed 阶段会逐步降低 temperature、增加 max tokens，目标是尽量稳定地拿到完整草案。compose 阶段除了重试，还会针对“天数不对、字段缺失、JSON 不可解析”这类错误做修复尝试。路线规划也有自己的重试逻辑，比如遇到限流类错误时会重试。

### Q39：你怎么做集成诊断？

**参考回答：**  
后端提供了 `GET /api/v1/plans/integrations/status` 接口，会返回 MCP 是否启用、是否连接、工具目录、工具映射、LLM 是否可用、地图渲染配置是否完整，以及当前 warnings。这个接口主要用于前端预检查和联调时快速判断问题是在模型、MCP 还是地图配置层。

### Q40：你为什么要单独返回 integration_status 和 map_config？

**参考回答：**  
因为这两个信息对前端非常关键，但它们不属于业务行程本身。`integration_status` 让前端能决定是否展示诊断面板或提示用户当前配置不完整，`map_config` 则告诉前端地图 SDK 是否可渲染、用什么 key 和中心点。这样前端不需要硬编码这些判断逻辑。

## 四、前端展示与交互实现

### Q41：前端整体是怎么设计的？

**参考回答：**  
前端是 Vue 3 + TypeScript + Vite。`App.vue` 负责整体状态管理和请求流程，用户先填表单发起规划，请求过程中会显示阶段性进度，结果回来后展示概览、每日行程、地图、轨迹和通知弹窗。组件层面拆成了表单发起、地图渲染、每日行程、Agent/Tool trace、通知弹窗等模块。

### Q42：前端为什么要做进度提示？

**参考回答：**  
因为这个请求链路相对长，用户体验上如果没有反馈，会误以为系统卡住了。我的做法是按“生成初步计划、搜索景点与餐饮、获取天气与路线、整合最终行程”几个阶段给一个渐进式进度条，虽然不是严格的实时进度，但能明显改善等待体验。

### Q43：地图是怎么渲染的？

**参考回答：**  
前端有一个 `AmapMap.vue` 组件，会根据后端返回的 `map_config` 动态加载高德 JS SDK，然后把 POI 坐标渲染成 marker，把路线 `polyline` 渲染成折线。地图是否可渲染取决于后端是否启用了地图配置、是否有 JS Key、是否有可用坐标数据。如果条件不满足，会展示明确的错误提示，而不是直接白屏。

### Q44：为什么地图配置放在后端返回，而不是前端写死？

**参考回答：**  
这样更利于环境隔离和统一控制。前端只根据后端返回的 `map_config` 判断是否能渲染，不需要自己猜测当前环境有没有 key、有没有启用地图、中心点应该放哪。对于联调和部署来说，这种后端驱动配置的方式也更稳。

### Q45：前端为什么要展示 Agent Trace 和 Tool Trace？

**参考回答：**  
一方面这是为了调试，另一方面也是为了体现系统不是黑盒。尤其在 AI Agent 场景里，面试官很容易问“你怎么知道哪一步出错了”。我前端把工具调用轨迹和参数展示出来，就是为了让问题更容易定位，也能更清楚地表达这是一个有可解释性的系统。

### Q46：前端怎么处理错误和 warning？

**参考回答：**  
我没有把后端原始错误直接抛给用户，而是做了一层用户友好的映射。比如天气失败会转换成“天气数据暂时不可用，但系统已继续生成”，路线失败会转换成“部分路线不可用，已保留基础行程安排”。真正的错误信息会保留在控制台或 trace 里，用户看到的是更容易理解的提示。

### Q47：为什么要做 PNG/PDF 导出？

**参考回答：**  
因为旅行规划是一个很适合分享和保存的结果。前端基于 `html2canvas` 和 `jsPDF` 做了导出，用户可以把完整结果保存成图片或 PDF。实现上我会先把所有天数展开，再截图导出，这样能确保导出的内容是完整的，不会只截到折叠状态的部分。

### Q48：这个前端最值得你讲的点是什么？

**参考回答：**  
我觉得最值得讲的不是 UI 本身，而是它如何承接后端的结构化结果。比如根据 `integration_status` 做预检查，根据 `map_config` 决定是否渲染地图，根据 `meta.warnings` 和 `tool_trace` 展示系统状态，根据每日 `route_summaries`、`weather`、`cost_breakdown` 去组织细节。也就是说，前端不是单纯展示一段文案，而是在消费一个设计过的结构化协议。

## 五、工程化、测试与部署

### Q49：你做了哪些测试？

**参考回答：**  
我主要做的是后端单元测试和关键流程测试，重点覆盖请求校验、天气失败时继续生成、酒店和天气并行编排、路线优先 MCP 再走 Web Service fallback、坐标缓存、POI detail 优化、seed 重试策略、compose 重试和修复、最终计划完整性校验、预算聚合和三餐补全等场景。这个项目里测试重点不是覆盖率数字，而是关键稳定性路径。

### Q50：你为什么把测试重点放在这些场景上？

**参考回答：**  
因为这类项目最容易出问题的不是页面能不能打开，而是链路是否稳定、结果是否完整。比如大模型输出不稳定、工具偶发失败、天气不可用、路线限流、天数不一致、预算不一致，这些都会直接影响最终体验。所以我优先把测试投在这些高风险点上。

### Q51：你做了哪些部署相关工作？

**参考回答：**  
我补了 Docker Compose 部署方案，把前后端都容器化了。后端镜像基于 Python 3.11，前端是 Node 构建加 Nginx 托管。部署时后端默认只绑定本地 `127.0.0.1:8000`，前端暴露公共端口。这样部署链路会更标准，前后端环境隔离也更清晰。

### Q52：GitHub Actions 自动部署是怎么做的？

**参考回答：**  
我配置了一个 `deploy.yml`，当代码 push 到 `main` 时，会先在 GitHub Runner 上安装前端和后端依赖，执行前端构建和后端测试。只有这些检查都通过后，才会通过 SSH 登录服务器，执行 `git pull` 和 `docker compose up -d --build`。这样可以避免有问题的提交直接部署到线上环境。

### Q53：为什么要把“构建和测试通过”放在部署前？

**参考回答：**  
这是最基本的发布门禁。尤其这个项目既有前端构建，又有后端测试，如果不先在 CI 里验证，直接在服务器上拉代码构建，风险会很高。把构建和测试前置可以在更早阶段拦住明显问题，也能减少服务器侧调试成本。

### Q54：你是怎么管理环境配置的？

**参考回答：**  
后端用 Pydantic Settings 读取 `.env`，前端通过 Vite 的环境变量读取 API 地址和开发面板开关。地图相关配置也做了区分，比如前端 JS SDK Key 和后端 Web Service Key 不混用。整体思路是把配置和代码分离，开发、生产通过不同 env 文件切换。

### Q55：这个项目的工程化边界在哪里？

**参考回答：**  
目前我认为它已经具备了本地开发、容器部署、CI 校验和自动化发布这些基本工程化能力，但还没有做到更完整的生产级观测和运维体系。比如还没有接入统一日志平台、指标监控、告警和更细粒度的 tracing，这部分如果继续往生产化推进，是下一步要补的。

## 六、深挖追问与风险权衡

### Q56：这个项目里你觉得最难的点是什么？

**参考回答：**  
我觉得最难的是把“不稳定的大模型输出”和“稳定的工程接口”接起来。大模型很容易在格式、字段完整性、天数一致性这些地方出问题，但前后端系统又要求结果必须结构稳定。所以我最后采用的是“LLM 生成 + 规则兜底 + 工具补事实 + 多层校验”这种折中方案。

### Q57：如果面试官质疑这不算真正的 AI Agent，你会怎么答？

**参考回答：**  
我会先认同这个项目不是完全自主的开放式 Agent，而是更偏工程化的编排式多 Agent。然后我会强调，这种设计是有意为之，因为旅行规划场景对结果结构和事实一致性要求很高。如果一开始就追求完全自主，反而更难保证稳定性。我的目标是先做一个可控、可解释、可验证的 Agent 系统。

### Q58：如果让你继续优化响应速度，你会怎么做？

**参考回答：**  
我会优先从三方面优化。第一是增加缓存，比如 POI detail、geocode 和热门城市查询缓存。第二是继续分析哪些阶段能并发，比如某些路线准备工作或 POI 细节拉取。第三是优化模型调用，比如更精简 prompt、控制返回长度、拆分只必要的上下文，减少 compose 阶段的负担。

### Q59：如果让你继续优化结果质量，你会怎么做？

**参考回答：**  
我会先把排序和选择策略做得更清晰，比如酒店、景点、餐饮不只是拿候选列表，而是引入更显式的打分逻辑。第二是让 route 和 hotel 的选择更强耦合，尽量减少跨城或跨区往返。第三是引入更多反馈闭环，比如把用户选择、导出或收藏行为作为后续优化依据。

### Q60：如果地图服务不可用怎么办？

**参考回答：**  
按当前实现，关键地图能力不可用时会直接失败，因为我希望返回的是“稳定可验证”的结果，而不是纯想象的文本计划。但从扩展角度看，可以进一步增加 mock、缓存或更弱的文本兜底模式。不过如果这样做，就要非常清楚地告诉用户当前结果是“低可信度”的建议，而不是精确规划。

### Q61：如果要支持英文城市名或国际化，你会怎么改？

**参考回答：**  
首先要放开 `destination` 的校验，然后补一层城市归一化和多语言地名映射。其次要确认底层地图服务是否覆盖这些区域，以及查询词、提示词、展示语言怎么统一。最后前端和后端的文案也要做国际化。这个改动不只是改一个正则，而是会牵涉输入约束、工具适配和结果展示三个层面。

### Q62：如果让你做真正生产化的可观测性，你会加什么？

**参考回答：**  
我会加结构化日志、阶段耗时统计、失败率统计、外部依赖调用状态和 trace ID。尤其是 Agent 场景下，我希望每次请求都能清楚看到 seed、POI、hotel、weather、route、compose 每一步花了多久，失败在哪，触发了几次重试。这样后续做优化和定位问题会更有效。

### Q63：如果让你做成本控制，你会怎么做？

**参考回答：**  
成本主要来自大模型调用和外部工具调用。我会优先减少不必要的 LLM token 消耗，比如压缩上下文、控制输出字段、避免重复汇总。工具层则通过缓存、候选数量限制、POI detail 限额和请求去重来控制。当前代码里其实已经有部分思路，比如 POI detail 的并发限制、数量限制和缓存。

### Q64：这个项目里你有没有做 fallback AI？

**参考回答：**  
代码里有 fallback 相关测试和基础方法，但在主流程里我没有把它作为正式默认路径启用。主链路仍然要求有可用的大模型配置，否则会直接失败。这个选择是为了让系统行为更清晰，避免看起来成功但质量不稳定。

### Q65：如果面试官问你“这个项目最能体现你什么能力”，你会怎么答？

**参考回答：**  
我会说最能体现的是“把不稳定的 AI 能力工程化”的能力。也就是我不是停留在能调用模型，而是把它放进了一个有 schema、有校验、有工具、有失败处理、有前端承接和工程化部署的完整系统里。这种能力比单纯做一个 prompt demo 更接近真实业务开发。

## 七、高频项目追问速答

### Q66：你在项目里最有成就感的一点是什么？

**参考回答：**  
最有成就感的是我把这个项目做成了“能解释、能校验、能降级”的系统，而不是一个黑盒生成器。尤其是 Agent trace、tool trace、结果修复和预算重算这些地方，能明显体现我对工程稳定性的重视。

### Q67：这个项目里你踩过的坑是什么？

**参考回答：**  
最大的坑就是大模型输出不稳定和外部工具返回不一致。比如有时候字段不全、天数不对、meal type 不统一，或者路线工具在不同模式下返回结构差异很大。我的应对方式是把这些不稳定点都吸收到适配层和规则层，而不是让它们直接暴露到前端。

### Q68：你如何证明这个项目不是“拼装 API”？

**参考回答：**  
我会强调两个点。第一，这个项目不是简单串 API，而是做了明确的 Agent 分工、状态编排和数据契约设计。第二，我对结果做了大量工程化处理，包括 schema 校验、重试、修复、降级、预算聚合、三餐补全、轨迹输出和测试覆盖，这些都是纯拼装项目通常不会做的。

### Q69：如果只让你挑一个技术点展开讲，你会讲哪个？

**参考回答：**  
我会讲“LLM 结构化输出稳定性”。因为这个点最能体现我对 AI 工程化的理解，也最容易展开到 prompt 约束、schema 验证、重试、修复、规则兜底和测试设计，能够把项目的深度讲出来。

### Q70：你会如何结束这段项目介绍？

**参考回答：**  
我通常会这样收尾：这个项目让我比较完整地实践了从 Agent 编排、工具集成、结构化输出控制，到前端承接、测试和部署的全链路能力，也让我更明确地理解了 AI 项目要落地，核心不是“模型能不能答”，而是“系统能不能稳定地产出可用结果”。

## 八、回答时的注意事项

- 不要说“我做了真正自主决策的通用 Agent”，当前项目更准确的说法是“编排式多 Agent”。
- 不要说“支持国际化旅行规划”，当前实现只支持中文城市名。
- 不要说“已经生产落地并有大量用户”，仓库里没有这类证据。
- 不要编造性能指标、接口耗时优化数据、测试覆盖率数字。
- 可以强调“稳定性策略、结构化约束、可解释性和工程化”。
- 被问到“如果继续做”时，再讲缓存、可观测性、排序策略、国际化和更强自主规划。
