# 智能旅游规划助手上线部署指南

更新日期：2026-03-14

本指南基于当前仓库结构编写：

- 前端：Vue 3 + TypeScript + Vite
- 后端：FastAPI
- 地图能力：高德地图 JS SDK + 高德 Web Service + MCP Server
- 大模型：OpenAI 兼容接口
- 当前仓库已自带 `frontend/Dockerfile`、`backend/Dockerfile`、`docker-compose.yml`

## 1. 先说结论

如果你现在的目标是“尽快稳定上线”，我最推荐你走这个方案：

**方案 A：1 台 Linux 云服务器 + Docker Compose + 域名 + HTTPS**

原因很简单：

1. 你这个项目前后端都已经有 Dockerfile，而且前端 Nginx 已经写好了 `/api/` 反向代理。
2. 后端依赖 `uvx` 启动 MCP，并且会拉起子进程，这种场景在单机 Docker 上最稳定、最可控。
3. 前后端同域部署后，CORS、跨域、前端 API 地址、地图加载这些问题都更少。
4. 后续如果你想迁移到更正式的云平台，也可以在这个基础上平滑升级。

## 2. 当前项目适合的上线方案

### 方案 A：单机 Docker Compose 部署

适合你现在这个项目，推荐优先使用。

优点：

- 和当前仓库最贴合
- 部署链路简单
- 前后端同域，配置少
- 最容易排查 MCP / 地图 / 模型连接问题

缺点：

- 需要自己维护服务器
- HTTPS、日志、备份需要自己配置

### 方案 B：前端静态托管 + 后端 Docker PaaS

可选组合：

- 前端上 Vercel
- 后端上 Render 或 Railway

优点：

- 前端部署体验好
- 自动构建、自动回滚、预览环境更方便

缺点：

- 前后端分离后，环境变量和跨域配置更多
- 后端依赖 MCP 子进程，必须优先使用 Docker 方式部署，不建议直接赌平台默认 Python Runtime
- 某些平台要求服务监听动态端口，当前仓库需要做一点适配

### 方案 C：传统 Linux 部署

即：Nginx + systemd + Python venv + 前端静态文件

优点：

- 最灵活
- 资源占用可控
- 适合后续做精细化运维

缺点：

- 步骤最多
- 维护成本最高
- 不如 Docker Compose 适合你当前阶段

## 3. 我建议你的上线顺序

建议按下面这个顺序推进：

1. 先用方案 A 把正式环境跑起来
2. 确认域名、HTTPS、地图、MCP、模型调用都正常
3. 再决定是否拆成“前端静态托管 + 后端独立服务”

如果你希望最稳，我建议不要一开始就拆平台。

# 方案 A：Docker Compose 单机上线

## 4. 上线前准备清单

你需要提前准备这些东西：

### 4.1 云服务器

建议：

- Ubuntu 22.04 LTS 或 24.04 LTS
- 2 核 4G 起步
- 系统盘至少 40GB

如果你只是自己试运行，2C4G 足够。
如果你后面打算公开给别人用，建议直接 4C8G。

### 4.2 域名

建议至少准备一个域名，例如：

- `travel.yourdomain.com`

### 4.3 第三方密钥

上线前至少准备好：

- 大模型 API Key
- 大模型 Base URL
- 大模型模型名
- 高德 JS API Key
- 高德安全密钥（如果启用安全校验）
- 高德 Web Service Key

### 4.4 仓库访问方式

你需要能在服务器上拉代码：

- Git HTTPS
- 或 Git SSH

## 5. 第一步：购买并初始化服务器

登录服务器后，先完成基础初始化。

建议执行：

```bash
sudo apt update && sudo apt upgrade -y
sudo timedatectl set-timezone Asia/Shanghai
```

然后新建一个部署目录，例如：

```bash
mkdir -p /opt/trip-planning-agent
cd /opt/trip-planning-agent
```

## 6. 第二步：安装 Docker 和 Docker Compose

推荐直接按 Docker 官方文档安装。

Ubuntu 官方安装入口：

- Docker Engine for Ubuntu: https://docs.docker.com/engine/install/ubuntu/
- Docker Compose install: https://docs.docker.com/compose/install/

安装完成后验证：

```bash
docker --version
docker compose version
```

如果你想让当前用户不带 `sudo` 使用 Docker，可执行：

```bash
sudo usermod -aG docker $USER
newgrp docker
```

## 7. 第三步：拉取项目代码

```bash
cd /opt

cd /opt/trip-planning-agent
```

建议先切到你准备上线的分支：

```bash
git checkout main
```

## 8. 第四步：配置生产环境变量

这是最关键的一步。

### 8.1 后端环境变量

当前仓库里已经有模板文件：

- `backend/.env.example`
- `backend/.env.production.example`

上线时不要直接使用示例值，建议复制成正式文件：

```bash
cp backend/.env.production.example backend/.env
```

然后编辑 `backend/.env`：

```env
APP_NAME=trip-planning-agent
APP_ENV=production
CORS_ORIGINS=["https://travel.yourdomain.com"]

OPENAI_API_KEY=你的大模型Key
OPENAI_BASE_URL=https://api-inference.modelscope.cn/v1
OPENAI_MODEL=Qwen/Qwen3.5-35B-A3B
OPENAI_TIMEOUT_SECONDS=60
OPENAI_MAX_RETRIES=1
OPENAI_TRUST_ENV=false

AMAP_API_KEY=你的高德JS_API_Key
AMAP_SECURITY_JS_CODE=你的高德安全密钥

AMAP_MCP_COMMAND=uvx
AMAP_MCP_ARGS=["amap-mcp-server", "stdio"]
AMAP_MCP_ENV={"AMAP_MAPS_API_KEY":"你的高德Web服务Key"}
AMAP_MCP_INHERIT_PROXY_ENV=false

AMAP_MCP_TOOL_POI_SEARCH=maps_text_search
AMAP_MCP_TOOL_ROUTE_PLAN=maps_direction_driving_by_address
AMAP_MCP_TOOL_WEATHER=maps_weather
AMAP_MCP_TIMEOUT_SECONDS=20
ENABLE_MOCK_MCP=false
```

### 8.2 前端环境变量

如果你采用“前后端同域 + 前端 Nginx 代理 `/api/`”的方式，前端最简单的配置是使用同域请求。

当前仓库已提供 [frontend/.env.production](/C:/Users/FFF/Desktop/trip-planning-agent/frontend/.env.production)，默认就是生产推荐值：

```env
VITE_API_BASE_URL=
VITE_SHOW_DEV_PANELS=false
```

说明：

- `VITE_API_BASE_URL=` 留空时，前端会直接请求 `/api/...`
- 这和你当前 `frontend/nginx.conf` 的反向代理方式最匹配

### 8.3 一个当前仓库里的重要注意点

当前仓库已经调整为生产更友好的 `docker-compose.yml`：`backend` 默认读取 `./backend/.env`，并且只绑定到宿主机本地回环地址。`frontend` 默认映射到 `127.0.0.1:8080`，`backend` 默认映射到 `127.0.0.1:8000`。这样更适合在服务器前面再接一层 Nginx 或 Caddy 来处理 80/443 和 HTTPS。

## 11. 第七步：绑定域名

如果你已经有域名，把域名解析到服务器公网 IP。

常见做法：

- `A` 记录指向服务器公网 IP
- 子域名例如 `travel.yourdomain.com`

解析生效后，再继续 HTTPS 配置。

---

## 12. 第八步：配置 HTTPS

生产环境一定建议加 HTTPS。

你有两种常见做法：

### 做法 1：服务器前面再放一层 Nginx / Caddy

职责分工：

- 外层 Nginx / Caddy：处理 80/443、证书、HTTPS 跳转
- 内层前端容器：继续监听 80，并代理 `/api/` 到 backend

这是我更推荐的方式，结构清晰，也方便后期统一管理证书。

### 做法 2：云厂商负载均衡 / CDN 终止 HTTPS

如果你本来就打算接 CDN 或负载均衡，也可以让它处理 HTTPS。

### 你当前阶段的建议

如果只是第一次上线，最省心的是：

- 服务器里跑当前这套 Docker Compose
- 服务器外层再加一个反向代理来处理 HTTPS

---

## 13. 第九步：开放防火墙和安全组

至少确认这些端口策略：

- `22`：只对你自己的管理 IP 开放更好
- `80`：对公网开放
- `443`：对公网开放

如果你暂时还没配 HTTPS，至少先开放 `80`。

# 方案 B：前端 Vercel + 后端 Render / Railway

## 15. 这个方案什么时候适合你

如果你更看重：

- 前端预览部署
- 自动构建
- 多环境管理
- Git push 后自动发布

可以考虑这个方案。

但对你当前项目来说，它**不是第一优先级**。

## 16. 为什么它不是第一优先级

因为你当前后端不是单纯的 HTTP API，它还依赖：

- MCP 子进程
- `uvx`
- 高德工具调用
- 外部 API 网络连通性

这会让“平台运行时差异”变成一个真实问题。

### 额外注意

Render 官方文档显示，Web Service 可以从 Git 仓库或 Docker 镜像部署，并且要求服务监听 `0.0.0.0`，默认端口期望是 `10000`，也可配置。

Railway 官方文档显示，它支持直接从仓库中的 `Dockerfile` 构建部署。

Vercel 官方文档显示，Vite 项目可以直接部署到 Vercel。

基于这些官方信息，我的判断是：

- 前端上 Vercel 没问题
- 后端如果上 Render / Railway，优先使用 Docker 方式
- 你需要确认后端容器监听端口和平台要求一致

## 17. 如果你要走这个方案，需要额外做的适配

### 17.1 前端

前端部署到 Vercel 时：

- Root Directory 设为 `frontend`
- Build Command 用 `npm run build`
- Output Directory 用 `dist`
- 环境变量里设置：

```env
VITE_API_BASE_URL=https://your-backend-domain.com
VITE_SHOW_DEV_PANELS=false
```

### 17.2 后端

后端部署到 Render / Railway 时：

- 优先选择 Docker 部署
- Root Directory 指向 `backend`
- 注入和 `backend/.env` 等价的环境变量
- 确认服务监听 `0.0.0.0`
- 确认平台要求的端口是否需要由环境变量 `PORT` 驱动

### 17.3 跨域

如果前后端分域名部署，例如：

- 前端：`https://travel.example.com`
- 后端：`https://api.example.com`

那你必须把后端 `CORS_ORIGINS` 改为：

```env
CORS_ORIGINS=["https://travel.example.com"]
```

# 方案 C：传统 Linux 部署

## 18. 什么时候考虑它

如果后面你要做：

- 更精细的日志分流
- systemd 服务管理
- 主机级 Nginx 配置
- 更低的容器开销

可以考虑这条路线。

## 19. 这条路线的大致结构

- 前端：本地构建 `dist`
- Nginx：托管静态文件并反代 `/api/`
- 后端：Python venv + `uvicorn`
- systemd：守护 FastAPI 进程

但对你现在的项目阶段，我不建议你先走这条。
