## 1. 开场介绍

### 30 秒版本

我做的是一个面向真实出行场景的 AI 智能旅游助手。用户输入目的地、天数、预算和偏好后，系统会生成结构化多日行程，并结合地图、天气、路线和预算信息做补全。它不是一次性生成 Demo，而是做成了可持续编辑的 Trip Workspace，支持固定预约、局部重规划、出发前预检、分享访问和 `.ics` 日历导出。

### 60 秒版本

这个项目的重点不是“调一次大模型”，而是把“生成、补事实、加约束、持续编辑、预检修复”串成闭环。  
后端基于 FastAPI 和多阶段 Agent 编排，先生成 seed itinerary，再结合高德地图能力补全 POI、酒店、天气和路线，最后输出稳定的结构化 `TravelPlan`。  
更关键的是，用户可以把结果保存成 Trip Workspace，继续录入预约、锁定日期、按天补缺口、刷新出发前预检，并查看最近一次重规划和预检摘要。最近一轮还把预检动作升级成了多动作修复入口，比如天气问题不只会提示“重排”，还会给出“改室内活动”和“调整出发时段”。

### 120 秒版本

我把这个项目定位成“AI 行程工作台”，而不是“AI 行程生成器”。  
它有两条核心链路：

1. 行程生成链路  
   用户请求进入 `planning.py` 和 `TravelPlannerService`，再由多阶段 Agent 编排生成结构化多日行程，并接入地图、天气、路线等事实能力做补全。
2. 工作区链路  
   用户可以把结果保存成 Trip Workspace，继续补充备注、录入固定预约、锁定部分日期、按天重规划、刷新预检、导出日历并分享访问。

我自己重点做了三类事情：

- 把 LLM 输出从一次性文本提升到结构化结果和多阶段编排
- 把 Trip Workspace、预约约束、缺口修复、预检刷新接成连续工作流
- 持续拆分前后端热点模块，让代码能支撑长期迭代，而不是功能越加越乱

## 2. 高频问答

### Q1：这个项目解决了什么问题？

大多数 AI 旅游产品只能给用户“看起来不错”的建议，但用户还得自己去核对地图、天气、路线和预约。  
这个项目解决的是“从建议到可执行计划”的落地问题：不仅生成结构化行程，还支持持续编辑、约束注入、局部修复、预检刷新和导出。

### Q2：为什么不是直接让大模型一次生成完？

因为旅游规划天然是多约束、多数据源问题。  
大模型适合做规划骨架和表达组织，但不适合单独承担 POI、天气、路线、营业时间、预约覆盖这类事实数据和规则约束。  
所以系统采用“模型负责生成 + 工具负责事实 + 规则负责校验和后处理”的分层方式。

### Q3：为什么要做多阶段 Agent 编排？

多阶段编排的价值是让每个阶段都能单独观测、单独优化、单独降级。  
如果所有事情都塞进一个大 prompt，排查和回归都会非常困难。  
现在的结构更利于：

- fallback
- telemetry
- diagnostics
- 针对单阶段优化
- 稳定回归测试

### Q4：Trip Workspace 的核心价值是什么？

它把“一次生成”升级成了“持续编辑”。  
用户可以保存请求和结果快照，录入固定预约，锁定部分日期，触发整程或单日重规划，刷新预检，并导出日历。  
从产品角度看，Trip Workspace 是系统从 Demo 走向真实工具的关键。

### Q5：固定预约是怎么做的？

我没有把预约做成备注字段，而是做成了工作区中的正式结构化约束。  
后端会做：

- 时间合法性校验
- 非酒店预约冲突校验
- 预约信息注入生成请求
- 生成后覆盖诊断 `reservation_coverage`
- 模型遗漏时的保底锚定回写

当前已经支持：

- 酒店 `check_in_slot / check_out_slot`
- 非酒店 `anchor_slot`
- 餐厅 `meal_slot`

### Q6：什么是预约覆盖诊断？

生成完成后，系统会检查每一条预约是否真的落到结果里，而不是只相信模型“应该记住了”。  
当前结果里有结构化的 `reservation_coverage`，会区分：

- `covered`
- `unresolved`
- `pending`

并保留目标天、匹配天和自动锚定天，前端会据此显示工作区中的预约状态。

### Q7：局部重规划和整天重规划有什么区别？

现在有两种模式：

- `replace`
  - 重新生成目标天
- `fill_gaps`
  - 尽量保留已有内容，只补缺口

`fill_gaps` 已经支持：

- 住宿
- 餐饮
- 早餐
- 午餐
- 晚餐
- 加餐
- 活动
- 预约
- 整天日程

这比“整天重来一次”更贴近用户真实需求。

### Q8：出发前预检现在做到了什么程度？

当前预检已经支持手动刷新，并记录 `last_precheck_summary`。  
会检查：

- 天气风险
- 路线缺失
- 营业时间缺失
- 预约未落地或仅保底注入

预检不是只展示状态，还会给出按天可执行的修复动作。  
例如天气问题当前会给出：

- 改室内活动
- 调整出发时段

路线问题会给出：

- 重排路线影响日
- 压缩跨区往返

### Q9：`.ics` 导出为什么值得讲？

因为它说明项目已经不只是“生成结果给你看”，而是开始考虑“结果如何带走并在真实工具里继续使用”。  
当前 `.ics` 导出会把工作区中的预约、住宿和显式活动导出成日历文件，直接提高可执行性。

### Q10：你最近做的最重要重构是什么？

不是单个函数优化，而是持续压缩热点模块。  
典型变化包括：

- 后端把编排和运行时逻辑继续拆到 `runtime / orchestration / helper`
- 工作区链路拆出 `replan / reservations / runtime / precheck / calendar`
- 前端把 `App.vue` 继续收缩成页面壳层，引入 `usePlannerViewModels.ts` 和 `usePlannerAppBridge.ts`
- 工作区动作、洞察、预检、预约面板进一步拆分

重构的目标不是文件变多，而是职责更清晰、功能能继续加下去。

### Q11：你怎么证明重构不是“为了重构而重构”？

我通常从两个维度回答：

1. 结构结果  
   热点文件职责更清晰，功能新增时不再只能回流到一个大文件。
2. 回归结果  
   当前本地基线是后端 `154 passed, 10 warnings`，前端类型检查和生产构建通过。

也就是说，重构不是单纯“挪文件”，而是在行为稳定的前提下改善可维护性。

### Q12：当前还有哪些明显可优化点？

后端仍偏厚的点主要是：

- `route_agent_orchestration.py`
- `ai_client_runtime_adapter.py`
- `amap_mcp_adapter_helpers.py`

前端仍需持续控制的点主要是：

- `PlannerRequestForm.vue`
- `DailyItineraryCard.vue`
- 页面级 bootstrap / shell 装配

另外，预约链路下一步适合继续走向更强的硬约束排程。

### Q13：如果继续做下一版，你会优先做什么？

我会优先做这几项：

1. 预约硬约束排程
2. 更细粒度的缺口修复
3. Google Maps 收藏点 / 清单导入
4. 更完整的 `.ics` 导出控制
5. 多方案 diff
6. 更自动化的出发前预检策略

这些方向和当前工作区主链路天然相连，投入产出比最高。

### Q14：和常见竞品相比，这个项目的差异是什么？

我通常会这样回答：

- 和只会生成 itinerary 的产品比，我们更强调工作区、约束和持续编辑
- 和只做地图导航的产品比，我们更强调多日规划和预约落地
- 和只做聊天问答的产品比，我们更强调结构化结果、可回填状态和局部修复

一句话说，就是它更接近“AI 行程工作台”，而不是“AI 攻略生成器”。

### Q15：为什么项目里装了 `.venv`，`pytest` 还是跑不起来？

最常见的原因不是“没装环境”，而是命令位置和解释器路径不一致。  
这个项目里，后端测试推荐这样跑：

在仓库根目录：

```powershell
& '.\backend\.venv\Scripts\python.exe' -m pytest -q backend\tests
```

如果已经进入 `backend`：

```powershell
& '.\.venv\Scripts\python.exe' -m pytest -q tests
```

核心原则是：显式用虚拟环境里的 Python 去启动 `pytest`，不要依赖外层环境碰运气。

## 3. 回答框架

如果面试官继续追问技术细节，建议按这个顺序回答：

1. 问题出现在哪一层
2. 业务影响是什么
3. 采取了什么方案
4. 如何验证方案有效

通用模板可以是：

“这个问题出现在工作区重规划 / 预约注入 / 预检刷新阶段，会直接影响用户对结果可执行性的信任。我先把约束显式建模，再把约束注入到生成请求，最后补上生成后的覆盖诊断或变更摘要，并用回归测试把行为守住。”

## 4. 可以主动反问面试官什么

如果面的是 AI 应用或智能体相关岗位，可以主动问：

- 你们更关注效果质量、时延还是成本？
- 线上是否有模型结果评估和回归机制？
- 工具调用是统一编排，还是各业务团队自己接？
- 岗位更希望候选人补强模型效果，还是补强工程稳定性？
