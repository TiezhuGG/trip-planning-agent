## 1. 开场介绍

### 30 秒版本

我做的是一个面向真实出行场景的 AI 智能旅游助手。用户输入目的地、天数、预算和偏好后，系统会生成结构化多日行程，并结合地图、天气和路线数据做补全。它不是一次性生成文案，而是做成了可持续编辑的 Trip Workspace，支持保存草稿、固定预约、局部重规划、分享访问和地图可视化。

### 60 秒版本

这个项目的重点不是“调一次大模型”，而是把“生成、补真值、校验、持续编辑”串成闭环。  
后端基于 FastAPI 和多阶段 Agent 编排，先生成 seed itinerary，再结合高德 MCP / Web Service 拉取 POI、酒店、天气和路线，最后组装成结构化 `TravelPlan`。  
我重点做了三类能力：

- 可靠性：主模型失败切备模、限流 fallback、地图层 MCP / Web Service 双通道兜底
- 一致性：通过 schema、归一化和后处理保证前端拿到的是稳定结构
- 产品化：引入 Trip Workspace，支持固定预约、覆盖审计、按天重规划和分享访问

### 120 秒版本

我把这个项目定位成“面向真实出行场景的 AI 应用工程化样板”。  
它有两条核心链路：

1. 行程生成链路  
   用户请求进入 `planning.py` 和 `TravelPlannerService`，再由 `PlanningCoordinatorAgent` 编排多阶段流程，结合 LLM 与地图工具生成结构化多日行程。
2. 工作区链路  
   用户可以把结果保存成 Trip Workspace，继续补充说明、录入固定预约、锁定部分日期，并发起整体或局部重规划。

最近一轮我还做了比较系统的重构：

- 前端把 `App.vue` 进一步拆成页面壳层、输入表单、结果展示、工作区面板、地图和 composable
- 前端新增 `usePlannerViewModels.ts` 和 `usePlannerAppBridge.ts`，把视图模型和事件桥接从页面壳层继续下沉
- 后端把 `planning_agent.py`、`route_agent.py`、`ai_client.py`、`amap_mcp_adapter.py` 等热点继续拆成 `runtime / orchestration / helper`
- 工作区与地图层继续做职责收缩，并用回归测试把行为守住

所以这个项目的价值不只是“功能能跑”，而是它已经具备继续往真实产品演进的工程基础。

## 2. 高频问答

### Q1：这个项目解决了什么问题？

多数 AI 旅游产品只能给出“看起来不错”的建议，但用户还得自己核对地图、天气、路线和预约。这个项目解决的是“从建议到可执行计划”的落地问题，把生成、补真值、保存工作区和持续编辑做成闭环。

### Q2：为什么不是直接调一次大模型？

因为旅游规划天然是多约束、多数据源问题。大模型适合生成与组织表达，但不适合单独承担路线、天气、POI、营业状态这类事实数据，所以必须把模型与工具拆开，各司其职。

### Q3：为什么要做多阶段 Agent 编排？

为了把职责拆清楚，避免一个黑盒 prompt 承担所有事情。多阶段编排之后，每个阶段都能单独观测、单独优化、单独降级，线上定位问题更直接。

### Q4：你怎么保证输出稳定？

主要靠四层：

- Pydantic schema 约束
- LLM JSON repair / retry
- 结果归一化与后处理收口
- fallback 和错误分类

也就是说，前端拿到的是稳定的结构化对象，而不是一段松散文本。

### Q5：Trip Workspace 的价值是什么？

它把“一次生成”升级成“可持续编辑”。用户可以保存草稿、继续补充备注、录入固定预约、锁定部分日期、发起局部重规划，还可以通过分享链接让别人访问当前工作区。

### Q6：固定预约是怎么做的？

我把预约做成了工作区里的正式约束，而不是备注字段。  
后端会做时间合法性校验、日期范围校验和非酒店类冲突校验；生成前把预约映射成约束注入请求；生成后再做覆盖审计，把没落进结果里的部分明确反馈给用户。

### Q7：外部依赖不稳定时怎么处理？

我没有把所有异常都打成 500，而是做了分层处理：

- 主模型失败时切备模
- 限流时走 fallback
- MCP 失败时按启动失败、映射错误、限流、网络错误分类
- 地图路线层保留 Web Service 兜底

目标是尽量做到“有结果且可解释”。

### Q8：最近一轮最重要的升级是什么？

从“一次性生成 Demo”升级成“可持续编辑的 AI 行程工作台”，并同步做了比较系统的结构重构。  
现在用户不仅能生成，还能保存、编辑、加预约、检查覆盖、锁定日期和局部重规划；代码层也不再依赖几个不断膨胀的超大文件。

### Q9：最近做了哪些重构？

我重点做了四块：

- 编排层：`planning_agent.py` 收缩为入口，核心运行时继续拆分
- 路线层：`route_agent.py` 和地图路由 runtime 继续分层
- 依赖适配层：`ai_client.py` 和 `amap_mcp_adapter.py` 继续拆成更明确的运行时结构
- 前端页面层：`App.vue`、工作区面板、预约面板、地图和 composable 继续收缩职责

### Q10：你怎么证明这些重构不是“为了重构而重构”？

我会从两个维度回答：

1. 结构结果  
   早期热点文件已经明显收缩，职责边界更清晰。
2. 回归结果  
   截至 2026-04-15，本地后端全量回归为 `131 passed, 8 warnings`，前端类型检查和构建都通过。

这说明不是只做了文件搬家，而是在保持行为稳定的前提下改善了可维护性。

### Q11：项目现在还有哪些明显可优化点？

最明显的几个点是：

- `route_agent_orchestration.py` 仍偏厚，路线生成和 truth binding 编排还比较集中
- `ai_client_runtime_adapter.py` 仍然装了不少请求模式切换、重试和降级逻辑
- `amap_mcp_adapter_helpers.py` 仍偏大，地图层胶水逻辑仍较集中
- 前端输入页和结果卡片还存在继续膨胀的风险，需要控制新增功能的落点

### Q12：如果继续做下一版，你会优先补什么？

我会优先做这几项：

1. 预约硬约束排程
2. 缺口驱动的一键补齐
3. Google Maps 收藏点 / 清单导入
4. 行程与预约 `.ics` 导出
5. 出发前二次校验
6. 多方案对比与差异说明

这些都直接提升真实可用性。

### Q13：和竞品相比，这个项目的差异是什么？

我会这样回答：

- 和只会聊天式推荐的产品比，这个项目更强调结构化结果与工作区持续编辑
- 和只做路线导航的产品比，这个项目更强调多日规划、预约约束和重规划
- 和只会生成一次性 itinerary 的 AI 工具比，这个项目更强调保存、分享、覆盖审计和局部修改

也就是说，它更接近“AI 行程工作台”，而不是“AI 攻略生成器”。

### Q15：为什么 pytest 在装了 `.venv` 后还是跑不起来？

最常见的原因不是“没装环境”，而是执行位置和解释器路径不一致。  
如果你在仓库根目录跑命令，应该显式用：

```powershell
& '.\backend\.venv\Scripts\python.exe' -m pytest -q backend\tests
```

如果你先 `cd backend`，再用：

```powershell
& '.\.venv\Scripts\python.exe' -m pytest -q tests
```

核心原则是：用虚拟环境里的 Python 去启动 pytest，不要依赖外层环境碰运气。

## 3. 回答框架

如果面试官继续深问，我建议按这个顺序回答：

1. 问题出现在哪一层
2. 业务影响是什么
3. 你采取了什么方案
4. 你如何验证方案有效

通用模板可以是：

“这个问题出现在工作区重规划阶段，会直接影响用户对固定预约约束的信任。我先把预约映射到 trip day 和时间窗，再把约束注入生成请求，最后补生成后的覆盖审计。验证方式是补回归测试，并在前端增加覆盖摘要和按天完成度反馈。”
