# 智能旅游助手：竞品对比与功能路线图

## 版本说明

- 文档基线时间：2026-04-15
- 说明：
  - 本文重点不是做最新市场事实核验，而是基于常见竞品形态与本项目当前代码能力，梳理差异化方向和下一阶段路线图。
  - 结论更偏产品工程判断，而不是市场份额判断。

## 1. 为什么现在要看竞品

项目已经不处在“能不能生成一份行程”的阶段，而是进入“能不能长期服务真实用户”的阶段。  
所以竞品对比的重点不再是页面风格，而是看四件事：

1. 用户已有资产能不能导入
2. 行程能不能持续编辑和协作
3. 结果能不能在出发前继续校验
4. 输出能不能真正带走使用

## 2. 用产品形态而不是单点功能看竞品

### 2.1 协作型旅行工作台

代表形态：Mindtrip 一类产品。

这类产品通常更强在：

- 协作
- 收藏和灵感沉淀
- 行前到行中的连续使用
- 用户已有旅行资产整理

对本项目的启发：

- 不能只做“生成结果”
- 要重视工作区、导入、分享、协作和结果沉淀

### 2.2 轻量型 AI itinerary 生成器

代表形态：Wonderplan 一类产品。

这类产品通常更强在：

- 快速生成
- 低门槛填写
- 快速修改
- 导出结果

对本项目的启发：

- 首次生成链路必须足够顺滑
- 不能让工作区能力把首屏使用门槛抬太高

### 2.3 对话型旅行助手

代表形态：GuideGeek 一类产品。

这类产品通常更强在：

- 随问随答
- 在途场景
- 低门槛入口

对本项目的启发：

- 未来可以补更轻的入口
- 但主价值仍应落在结构化结果和工作区，不要反过来退化成聊天机器人

### 2.4 地图型基础设施产品

代表形态：Google Maps 一类产品。

这类产品通常更强在：

- 收藏点和清单
- 导航与 ETA
- 用户长期沉淀资产
- 在途使用频率

对本项目的启发：

- “导入已有资产”非常重要
- “导出到用户已有工具”同样重要

## 3. 本项目当前的相对位置

### 3.1 已经明显强于普通 AI 行程 Demo 的地方

- 输出结构化多日 `TravelPlan`
- 有 Trip Workspace 持续编辑模型
- 有固定预约录入、校验、覆盖诊断和保底锚定
- 支持整程重规划和单日缺口修复
- 有出发前预检刷新与摘要
- 有 `.ics` 日历导出
- 有地图、天气、路线、预算等事实数据补全

### 3.2 仍明显弱于成熟产品的地方

- 用户已有收藏点、清单、确认单导入能力不足
- 工作区协作能力还停留在分享访问，未深入到评论、diff、权限
- 导出能力已有基础版，但还不够细
- 在途场景入口较弱
- 多方案对比和决策支持不足

## 4. 当前差异化优势应该怎么讲

如果从产品定位讲，本项目的差异化优势不是“聊天更聪明”，而是这四点：

1. 结构化行程，而不是纯文本建议
2. 工作区持续编辑，而不是一次生成结束
3. 预约约束和覆盖诊断，而不是只记录预约信息
4. 缺口修复和预检刷新，而不是只会“重新生成一次”

一句话总结：

> 这是一个正在成型的 AI 行程工作台，而不是单次输出的 AI 攻略生成器。

## 6. 功能路线图

### P0：优先级最高

#### 1. 预约硬约束排程继续做深

当前已经有：

- 预约注入请求
- `anchor_slot / meal_slot / check_in_slot / check_out_slot`
- `day_anchor_plan`
- 同日多预约先后顺序协调
- 生成后覆盖诊断
- 保底顺序锚定
- 前端覆盖卡片和日准备度解释

下一步应该做的是进一步压实约束，让预约不仅“尽量被满足”，而是更明确地占据日程槽位，并在冲突时给出更明确的取舍和失败解释。

价值：

- 直接提升结果可执行性
- 降低“有预约但日程里看不见”的风险
- 提升同一天多硬约束场景下的稳定性

#### 2. 更细粒度的缺口修复

当前 `fill_gaps` 已支持：

- 住宿
- 餐饮
- 早餐 / 午餐 / 晚餐 / 加餐
- 活动
- 预约
- 整天日程

下一步应该继续做：

- 更细的字段级修复
- 不同问题类型对应不同 repair 策略
- 更明确的修复前后 diff

价值：

- 比整天重生更贴近真实用户操作
- 能把“发现问题”进一步升级为“快速修掉问题”

#### 3. 工作区预检动作继续产品化

当前预检已支持多动作：

- 天气：改室内活动、调整出发时段
- 路线：重排路线影响日、压缩跨区往返
- 营业时间：替换活动、调整游玩时段
- 预约：处理预约

下一步可以继续做：

- 动作优先级
- 动作执行后 diff
- 自动推荐最优动作

价值：

- 让预检从“状态面板”变成“修复入口”

### P1：第二阶段

#### 4. Google Maps 收藏点 / 清单导入

这是最值得补的用户资产导入能力之一。

价值：

- 缩短从“已有偏好”到“生成工作区”的路径
- 对齐地图型产品的长期资产优势

#### 5. `.ics` 导出增强

当前基础版已打通。下一步建议做：

- 导出范围选择
- 活动粒度控制
- 导出字段补齐
- 与预检提醒联动

价值：

- 提高真实落地使用率
- 强化“结果可以带走”的产品感

#### 6. 多方案对比与 diff

同一请求输出多种方案，例如：

- 省钱版
- 均衡版
- 深度版

并支持工作区级别 diff。

价值：

- 把 AI 从“给答案”提升到“辅助决策”

### P2：第三阶段

#### 7. 收据 / 确认单导入

允许用户导入邮件确认单、截图或文本内容，自动生成预约草稿。

价值：

- 和预约链路天然衔接
- 对真实使用价值很高

#### 8. 协作能力增强

在当前分享访问基础上增加：

- 评论
- 变更记录
- 只读 / 可编辑权限
- 方案比较视图

价值：

- 让工作区从“可分享”进一步升级为“可协作”

#### 9. 在途模式

当前项目更偏行前规划，后续可补：

- 当天模式
- 快速重排
- 基于天气和拥堵的即时提醒

价值：

- 覆盖用户旅行中的高频场景

## 8. 现在最值得做的，不是最多，而是最顺着主链路

如果只看当前代码和产品演进路径，最值得继续做的不是“再做一个聊天框”，而是：

1. 继续把预约硬约束从“基础落地”推进到“稳定可解释”
2. 继续把缺口修复做深
3. 继续把预检动作做成真正可执行的修复入口
4. 补上导入和导出能力
5. 增加多方案 diff

这五类能力都与当前工作区主链路天然相连，投入产出比最高。

## 9. 一句话结论

从竞品视角看，这个项目当前已经在“结构化行程 + 工作区 + 预约约束 + 局部修复 + 预检刷新”上形成了很强的产品基础；下一阶段最值得做的，不是重复建设聊天入口，而是把导入、导出、硬约束和多方案决策能力补齐。
